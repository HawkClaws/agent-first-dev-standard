# エージェント前提開発基準 (Agent-First Development Standard)

コーディングエージェント(Claude Code、Codex 等)に実装を委譲することを前提とした開発チームのための、理解・PR・マージ・レビューの運用基準。

特定のエージェント製品には依存しません。どのエージェントを使うチームでも(混在していても)適用できます。

### 🗺 まずはこの1枚 — [導入前後のフロー比較図](https://hawkclaws.github.io/agent-first-dev-standard/flow-comparison.html)

この基準を入れると、開発フローの**何が変わり、何が変わらないか**を1画面で見られます。基準本文を読む前の全体像として、また導入をチームに提案するときの説明用に。

## 導入(3ステップ)

**エージェントに頼めます。** このリポジトリをクローンして、コーディングエージェントに「**この基準を導入したい**」と言えば、下の3つは全部やってくれます。**ただし他人のリポジトリにファイルを書き込む作業なので、何をどこに置くかを先に見せて確認を取ってから書かせてください。**

以下は手でやる場合の内容です。

**1. スキルをコピーする**

```bash
git clone https://github.com/HawkClaws/agent-first-dev-standard.git
cd agent-first-dev-standard

# Claude Code
cp -r skills/* <your-repo>/.claude/skills/

# Codex CLI
cp -r skills/* <your-repo>/.agents/skills/
```

エージェント製品には依存しません。上記以外でも、各 `SKILL.md` はそのままカスタム指示として使えます。詳細は [skills/README.md](skills/README.md)。

**2. ツール制限付きのサブエージェント定義を置く**(独立照合の自動版——テストコードか結合テスト仕様書の生成——を使う場合のみ)

`skills/crosscheck/SKILL.md` の中にある定義例を `<your-repo>/.claude/agents/spec-test-writer.md` に置きます。**既定の人間版だけを使うなら不要です。**

**3. PRテンプレートを配置する**

`skills/pr-guide/assets/pr-template.md` を、フォージのテンプレート置き場(`.github/PULL_REQUEST_TEMPLATE.md` など)にコピーします。

以上です。**この時点ではまだ何も義務は発生しません。** 地図を先に用意する工程もありません——地図は**その領域に初めて触るPRの中**で作ります([standard.md §12](standard.md#s12))。

## 使い方

```
/flow <チケットID> <チケットの本文、またはURL・パス・Issue番号>
```

**これだけです。** 機械でできる工程(下書き・機械検査・突き合わせ・記録)を連続実行し、**人間の判断が必要なところは停止でまとめて聞いてきます**——標準ケースで**停止は3回**(着手/PR確認/マージ)。👤 の項目数は減らしていません。聞く場所を束ねただけです(止まるたびに、フロー全体のどこにいるか・あと何回止まるか・次に止まるまで何分走るかを先頭に出す)。答えて、もう一度 `/flow <チケットID>` を呼べば続きが走ります(2回目以降は状態ファイルがあるのでIDだけでよい)。実装の完了待ちの後に**判断ゼロの継続呼び出し**が1回入ります(完了通知が届く環境では人の操作なし)。

**チケットの本文かその在り処を渡してください。** この基準はチケットの置き場所を規定していません(Issue・Jira・Notion・リポジトリ内のファイル、どれでも構いません)。渡されなければエージェントは聞いてきます——**薄いチケットを勝手に補完させないため**です。**設計メモもチケットと同じ場所に置きます**(合意が成立したら `承認: 日付 役割` を1行追記。在り処は状態ファイルに記録され、実装の委譲と照合はそこから辿ります)。

状態は**リポジトリの外** `~/.flow/<リポジトリ名>/<チケットID>.md` のチェックリストに残ります(リポジトリには何も入りません。ブランチを切り替えても消えず、実装エージェントの目にも入りません)。**この `👤` 付き項目の一覧が、そのチケットで人間が担当した範囲そのもの**です。

### 複数チケットを同時に進める

フローは1チケット=1状態ファイルなので、同時に進めるかどうかはフローの中身ではなく**状態ファイルを何枚開くか**で決まります。フローに並列用の分岐はありません。

**設計は並行、実装は直列**(作業ツリーが1つのとき。既定の形)

1. 各チケットで `/flow <ID> <本文>` を呼ぶ。設計メモはコードを触らないので、同じ作業ツリーで何本呼んでも衝突しない。全部「設計メモへの合意」で止まる
2. 設計メモをまとめて読み、合意する
3. **1本目だけ** `/flow <ID>` を再度呼ぶ。実装の委譲 → 期待値の書き出し(委譲直後・同じ停止の中で聞き取り。実装と並列)→ PR確認 → マージ、まで進める
4. マージしてから2本目の `/flow <ID>`(ブランチは main から切り直す)。以下同じ

「マージしてから次」を守らせる検査機構は、`/flow` にはありません(git の観測値から「マージ済みか・実装中か」を判定する機構は、マージ方式や git 運用をどれか決め打ちして必ず誤判定する。経緯は CHANGELOG v0.35)。代わりに `/flow` は**止まって報告するたび、未マージのブランチ一覧(`git branch --no-merged <切り元>`)を現在地に1行で写します**。判定も削除もしない、読み流せる計器です。委譲は設計メモの合意(👤)の直後なので、人間は委譲の前に必ずこの行を見る位置にいます。

実装を直列にするのは、作業ツリーが1つだからだけではありません。**期待値の書き出しは人間が実装を見る前に書く作業**で、3本ぶん同時に来ると切り替えの負荷がそのまま検査の質に乗ります。1本ずつ回すと、フローが想定している「1本の実装が走っている間に、その1本の期待値を書く」形に収まります。

**実装まで並行**(作業ツリーを分けられるとき)

条件が2つあります。
- **触る領域が別であること。** 同じ領域を2本が触ると、地図の初版が両方のPRで作られて衝突します(初版は領域ごとに一度だけ)
- **作業ツリーが別であること。** チケットごとに別リポジトリなら何もしなくてよい。同じリポジトリなら、並列で進めると人間が明示的に選べば `/flow` が `git worktree add` で専用の作業ツリーを作ってから委譲します(切り元が申告ではなく実行になる)。未追跡ファイル(.env 等)や venv・node_modules は worktree に来ないので、環境の再構築コストは実測表に残します。マージ後の `git worktree remove` は人間の仕事です

どちらの形でも:
- **セッションはチケットごとに1つ。** 1つのセッションに2本を混ぜると「現在地」の報告が混ざります
- **照合メモの置き場所はチケットIDで分ける**(リポジトリの外、`~/crosscheck/<ID>.md` など)
- **実測表の備考に「同時進行: <他のID> / 実装順: n番目(決めた者)」を残す。** 並行時の人間の待ちが直列時とどう違うかは、この記録が3件たまるまで分かりません。設計段階の調査を深くする・フローを分ける等の変更は、その実測が出てから判断します(CHANGELOG v0.29)

### 人間に聞かれること(全10個。標準ケースでは停止3回にまとめて聞かれます)

**答えるだけのもの(6個)**

| 何を | 誰が |
|---|---|
| 設計メモの方針でよいか(不可逆系なら明示承認)〔停止1〕 | チーム / ドメインオーナー |
| 突き合わせの食い違いは「仕様が2通りに読めた(A)」か「知らなかった(B)」か。Bなら反映先はどこか〔停止2。v0.37で明示化——仕事自体は§4が最初から著者に割り当てていたもの〕 | PR著者 |
| この変更が触る領域はどれか(機械が diff から仮決めし、人が確定する)〔停止2〕 | ドメインオーナー |
| 理解レベル(行/構造/契約)の確定〔停止2。裁定が発生したら裁定後〕 | ドメインオーナー |
| 食い違いをどちらの解釈で裁くか〔独立照合のとき〕 | 仕様の持ち主 |
| マージするか〔停止3〕 | マージする人 |

**書く作業があるもの(4個。自動版の出力が結合テスト仕様書のときは+1)** — ここは答えるだけでは済みません

| 何を | 誰が | 何をする |
|---|---|---|
| **地図の初版の検収** | その領域のドメインオーナー | 初回のみ。最低ライン: Level 2(不変条件)・3(危険領域)の**通読と修正**。無修正の受け入れは読まれていない疑い |
| **期待値の書き出し(理解検査・標準)** | PR著者 | 実装の出力を見る**前**に、契約を自分の言葉で言い直す(成功したら/失敗したら/前提。**参照先の切り替えなど成否で分かれない変更は1問1答でよい**)。**エージェントの質問に口頭で答える形でもよい**。書けない欄・差の扱いは [crosscheck](skills/crosscheck/SKILL.md) |
| **期待値の書き出し(独立照合・不可逆系は必須)** | 実装方針を書いていない人(レビュアー) | 仕様だけを見て、期待する入出力を書き出す(直接編集か、エージェントの聞き取り)。**実装と並列にやれるのでリードタイムは伸びない** |
| **採らなかった選択肢** | PR著者 | 捨てた案と理由。本人の発言の逐語転記は可(選別は著者)、生成・整形は不可 |
| **結合テスト仕様書の実行**(自動版の出力が仕様書のときのみ) | PR著者 | 実物相当で項目ごとに手順を実行し、観測した値と 一致/食い違い/実行できず を書く。期待結果は直さない。食い違いは裁定へ。判断ではないので👤には数えないが、作業時間はかかる |

期待値と選択肢の3つは**AIに生成させると意味が消えます**(記録の転記は例外——出所を明記した転記は生成ではありません)。理解検査の期待値は、エージェントに埋めさせた時点で検査ではなくなります。独立照合の期待値は、実装を見た人が書くと自己照合になります。

### 全部が毎回走るわけではありません

- **地図に触るのはPR作成の段だけ**です。着手時には触りません。**初版は領域ごとに一度だけ**で、2回目以降は飛びます
- **理解検査**(著者が実装の出力を見る前に期待値を書く)が標準です。**独立照合**(第二解釈者)は不可逆系(スキーマ変更・データ移行・課金・外部送信・削除)に触るときだけ必須(一人運用で第二解釈者がいなければ自動版で満たす)。契約理解レベルのコードにはどちらも任意です
- **出力との突き合わせ**(実データを1本通して分布と集計を見る)は、計測・集計・エクスポート系——値を人間が読んで判断する成果物——だけ必須です
- **結合テスト**(箱の境界を越える契約を、依存の実物か実物相当を通して固定するテスト)は、変更が箱の境界を越えるときだけ必須です。単体テストと同じくエージェントが書きます——委譲の範囲は結合テストまで([§4](standard.md#s4)「委譲の範囲」)。リポジトリに実行手段が無ければ委譲の中では作らず「未実施」と記録し、基盤の整備は別チケットにします
- **結合テスト仕様書**(人が実行する試験項目の一覧)は、機械が回せない境界(自動の実行手段が無い境界)や、文書としての納品・監査が要るときに、**実装を見せないサブエージェントに仕様から書かせます**——独立照合の自動版の出力形式の一つで、テストコードと同じ隔離条件です([§4](standard.md#s4))。実行するのは人で、実行先は実物相当(サンドボックス・検証環境)に限ります——不可逆系の境界を本番で確かめることは人にも許しません。観測を書いてから一致/食い違いを書き、食い違いは裁定へ。仕様書は回帰を固定しないので、実行手段が整った境界からコードに移します
- 不要な工程は `[~]` にして**理由を書きます**。この記録が、重すぎる項目を削る根拠になります([§12](standard.md#s12))

### 実測(1周回したときの目安)

| 工程 | 所要 |
|---|---|
| 設計メモ+承認 | 25秒(機械)+ 合意(人間) |
| 実装+単体テスト | 3〜4分(結合テストを指示していない時点の実測。v0.39 で委譲の範囲が結合テストまで広がった分は未実測) |
| 地図の初版生成(領域の初回だけ) | 20秒(機械)+ 検収(人間) |
| 理解検査(期待値の書き出し) | **実装と並列。クリティカルパス0分**(記入は契約1本あたり数分) |
| 独立照合 | **実装と並列。クリティカルパス0分** |
| AI一次レビュー | 6分 |
| 裁定+書き戻し | 2分(人間) |

## 思想(3行)

- 「全部読む」は物理的に破綻した。「読まない」は障害の夜に破綻する。この基準は、その間に線を引くための道具である
- 人間の理解はレビューのためではなく、将来の保守・障害対応・意思決定のためにある
- 守られない基準は無いより悪い。重すぎる項目は厳格化ではなく削除する

## このリポジトリの範囲

一般原則のみを含みます。特定の組織への適用(実測値・閾値・チーム構成・チケット運用)は各組織の内部ドキュメントとして管理し、このリポジトリには含めません。適用する場合は、内部ドキュメント側に「本基準 vX.X に準拠」と明記し、更新への追従は意識的に行うことを推奨します。

## 関連する先行事例・研究(2026年8月調査)

主要OSSプロジェクトのAI生成コードポリシーは、いずれも一律の扱いを定めている:[QEMU](https://www.qemu.org/docs/master/devel/code-provenance.html)(AI生成コンテンツを拒否)/ [Gentoo](https://wiki.gentoo.org/wiki/Project:Council/AI_policy)(全面禁止)/ [NetBSD](https://www.netbsd.org/developers/commit-guidelines.html)(汚染推定+コア承認)/ [Fedora](https://communityblog.fedoraproject.org/council-policy-proposal-policy-on-ai-assisted-contributions/)(許可+説明責任と開示。提案は2025年10月に[承認](https://lwn.net/Articles/1042947/))/ [curl](https://github.com/curl/curl/blob/master/docs/CONTRIBUTE.md)(通常品質基準+開示)。

実務側の報告として、「全員が1行も手で書かない」チームの1年間([木村健一郎, 2026-08](https://speakerdeck.com/kenichirokimura/embedding-ai-driven-development-into-your-team))は、生成コードの説明責任を指示した人間に置く点・レビューを設計判断へ寄せる点・役割ごとにエージェントを分割する点で本基準と同じ形に収束している。同報告の「手で書く前に疑う順番」([§8](standard.md#s8))・「途中参加者の合流を検査に使う」([§11](standard.md#s11))・「手順書自体の肥大化」([§7](standard.md#s7))は本基準に取り込んだ。定量評価ではない。

コードの性質に応じて**理解の深さを段階化**した公開基準は、これらにも政府系ガイドラインにも確認できていない。関連研究として、リスクに応じて監督形態を段階化する [Graduated Human Oversight(arXiv:2606.22484)](https://arxiv.org/pdf/2606.22484) がある(軸が異なる)。「無い」ことの証明はできないので、既存の類似基準をご存知であればissueで教えてほしい。
