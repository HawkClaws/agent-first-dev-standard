# エージェント前提開発基準 (Agent-First Development Standard)

コーディングエージェント(Claude Code、Codex 等)に実装を委譲することを前提とした開発チームのための、理解・PR・マージ・レビューの運用基準。

特定のエージェント製品には依存しません。どのエージェントを使うチームでも(混在していても)適用できます。

### 🗺 まずはこの1枚 — [導入前後のフロー比較図](https://hawkclaws.github.io/agent-first-dev-standard/flow-comparison.html)

この基準を入れると、開発フローの**何が変わり、何が変わらないか**を1画面で見られます。基準本文を読む前の全体像として、また導入をチームに提案するときの説明用に。

## 導入(3ステップ)

**エージェントに頼めます。** このリポジトリをクローンして、コーディングエージェントに「**この基準を導入したい**」と言えば、下の3つは全部やってくれます。**ただし他人のリポジトリにファイルを書き込む作業なので、何をどこに置くかを先に見せて確認を取ってから書かせてください。**

以下は手でやる場合の内容です。

**1. スキルをコピーする**

```bash
git clone https://github.com/HawkClaws/agent-first-dev-standard.git
cd agent-first-dev-standard

# Claude Code
cp -r skills/* <your-repo>/.claude/skills/

# Codex CLI
cp -r skills/* <your-repo>/.agents/skills/
```

エージェント製品には依存しません。上記以外でも、各 `SKILL.md` はそのままカスタム指示として使えます。詳細は [skills/README.md](skills/README.md)。

**2. ツール制限付きのサブエージェント定義を置く**(独立照合の自動版を使う場合のみ)

`skills/crosscheck/SKILL.md` の中にある定義例を `<your-repo>/.claude/agents/spec-test-writer.md` に置きます。**既定の人間版だけを使うなら不要です。**

**3. PRテンプレートを配置する**

`skills/pr-guide/assets/pr-template.md` を、フォージのテンプレート置き場(`.github/PULL_REQUEST_TEMPLATE.md` など)にコピーします。

以上です。**この時点ではまだ何も義務は発生しません。** 地図を先に用意する工程もありません——地図は**その領域に初めて触るPRの中**で作ります([standard.md §12](standard.md#s12))。

## 使い方

```
/flow <チケットID> <チケットの本文、またはURL・パス・Issue番号>
```

**これだけです。** 機械でできる工程(下書き・機械検査・突き合わせ・記録)を連続実行し、**人間の判断が必要なところで止まって聞いてきます。** 答えて、もう一度 `/flow <チケットID>` を呼べば続きが走ります(2回目以降は状態ファイルがあるのでIDだけでよい)。

**チケットの本文かその在り処を渡してください。** この基準はチケットの置き場所を規定していません(Issue・Jira・Notion・リポジトリ内のファイル、どれでも構いません)。渡されなければエージェントは聞いてきます——**薄いチケットを勝手に補完させないため**です。補完された内容は独立照合の材料になるので、そこで著者の解釈が仕様に化けます。

状態は `docs/flow/<チケットID>.md` のチェックリストに残ります。**この `👤` 付き項目の一覧が、そのチケットで人間が担当した範囲そのもの**です。

### 人間に聞かれること(全10個)

**答えるだけのもの(6個)**

| 何を | 誰が |
|---|---|
| この変更が触る領域はどれか(PR作成時。**一人運用など選択肢が実質1つなら、機械が決めて人が見て止める形でよい**——「機械が決めた」と記録) | ドメインオーナー |
| 生成された地図の初版を検収するか(最低ライン: **Level 2・3 の通読と修正**。機械の事実検証を前処理に使ってよい。**その領域の初回だけ**) | その領域のドメインオーナー |
| 設計メモの方針でよいか(不可逆系なら明示承認) | チーム / ドメインオーナー |
| 食い違いをどちらの解釈で裁くか | 仕様の持ち主 |
| 理解レベル(行/構造/契約)の確定 | ドメインオーナー |
| マージするか | マージする人 |

**書く作業があるもの(3個)** — ここは答えるだけでは済みません

| 何を | 誰が | 何をする |
|---|---|---|
| **期待値の書き出し(理解検査・標準)** | PR著者 | 実装の出力を見る**前**に、契約を自分の言葉で言い直す(成功したら/失敗したら/前提。**参照先の切り替えなど成否で分かれない変更は1問1答でよい**)。**エージェントの質問に口頭で答える形でもよい**。書けない欄があること自体がシグナル(全契約が同じ理由で空くなら理解不足ではなく器の不一致——器を替える)。差の行き先は種別で分かれる——A(仕様が2通りに読めた)はPRの欄で裁定、B(知らなかった)はコメント・地図へ反映 |
| **期待値の書き出し(独立照合・不可逆系は必須)** | 実装方針を書いていない人(レビュアー) | 仕様だけを見て、期待する入出力を書き出す(直接編集か、エージェントの聞き取り)。**実装と並列にやれるのでリードタイムは伸びない** |
| **採らなかった選択肢** | PR著者 | 捨てた案と理由。**本人の発言(会話ログ等)の逐語転記は可**(出所明記・どれを載せるかの選別は著者)。AIが生成した案の列挙や、整形・言い換えを伴う転記は不可 |

この3つは**AIに生成させると意味が消えます**(記録の転記は例外——出所を明記した転記は生成ではありません)。PRの「一番怪しい箇所」は著者が書く欄ではなくなりました——実装側の申告と設計メモの懸念点を機械が転記し、著者は見て違うものを消すだけです。理解検査の期待値は、エージェントに埋めさせた時点で検査ではなくなります。独立照合の期待値は、実装を見た人が書くと自己照合になります。

### 全部が毎回走るわけではありません

- **地図に触るのはPR作成の段だけ**です。着手時には触りません。**初版は領域ごとに一度だけ**で、2回目以降は飛びます
- **理解検査**(著者が実装の出力を見る前に期待値を書く)が標準です。**独立照合**(第二解釈者)は不可逆系(スキーマ変更・データ移行・課金・外部送信・削除)に触るときだけ必須。契約理解レベルのコードにはどちらも任意です
- **出力との突き合わせ**(実データを1本通して分布と集計を見る)は、計測・集計・エクスポート系——値を人間が読んで判断する成果物——だけ必須です
- 不要な工程は `[~]` にして**理由を書きます**。この記録が、重すぎる項目を削る根拠になります([§12](standard.md#s12))

### 実測(1周回したときの目安)

| 工程 | 所要 |
|---|---|
| 設計メモ+承認 | 25秒(機械)+ 合意(人間) |
| 実装+テスト | 3〜4分 |
| 地図の初版生成(領域の初回だけ) | 20秒(機械)+ 検収(人間) |
| 理解検査(期待値の書き出し) | **実装と並列。クリティカルパス0分**(記入は契約1本あたり数分) |
| 独立照合 | **実装と並列。クリティカルパス0分** |
| AI一次レビュー | 6分 |
| 裁定+書き戻し | 2分(人間) |

## 思想(3行)

- 「全部読む」は物理的に破綻した。「読まない」は障害の夜に破綻する。この基準は、その間に線を引くための道具である
- 人間の理解はレビューのためではなく、将来の保守・障害対応・意思決定のためにある
- 守られない基準は無いより悪い。重すぎる項目は厳格化ではなく削除する

## このリポジトリの範囲

一般原則のみを含みます。特定の組織への適用(実測値・閾値・チーム構成・チケット運用)は各組織の内部ドキュメントとして管理し、このリポジトリには含めません。適用する場合は、内部ドキュメント側に「本基準 vX.X に準拠」と明記し、更新への追従は意識的に行うことを推奨します。

## 関連する先行事例・研究(2026年8月調査)

主要OSSプロジェクトのAI生成コードポリシーは、いずれも一律の扱いを定めている:[QEMU](https://www.qemu.org/docs/master/devel/code-provenance.html)(AI生成コンテンツを拒否)/ [Gentoo](https://wiki.gentoo.org/wiki/Project:Council/AI_policy)(全面禁止)/ [NetBSD](https://www.netbsd.org/developers/commit-guidelines.html)(汚染推定+コア承認)/ [Fedora](https://communityblog.fedoraproject.org/council-policy-proposal-policy-on-ai-assisted-contributions/)(許可+説明責任と開示。提案は2025年10月に[承認](https://lwn.net/Articles/1042947/))/ [curl](https://github.com/curl/curl/blob/master/docs/CONTRIBUTE.md)(通常品質基準+開示)。

コードの性質に応じて**理解の深さを段階化**した公開基準は、これらにも政府系ガイドラインにも確認できていない。関連研究として、リスクに応じて監督形態を段階化する [Graduated Human Oversight(arXiv:2606.22484)](https://arxiv.org/pdf/2606.22484) がある(軸が異なる)。「無い」ことの証明はできないので、既存の類似基準をご存知であればissueで教えてほしい。
