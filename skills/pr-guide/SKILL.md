# PRガイドの下書き(基準[§9](../../standard.md#s9)の実装)

レビュアーの限られた注意力を正しい場所に配分するためのPR説明を下書きする。**このスキルは判断欄を生成しない**——それがこのスキルの一番大事な仕様である。

## 手順

1. diffとチケット(あれば設計メモも)を読む
2. [PRテンプレート](assets/pr-template.md)の**機械記入欄**を埋める(このファイルが正本。複製は置かない):
   - **TL;DR「何を」「なぜ」**(各40字以内。「なぜ」はチケットに書いていない背景を優先)
   - **レビュー指定**: diffから不可逆な副作用(スキーマ変更・マイグレーション・データ変更・課金・外部送信・削除)、セキュリティ境界、並行処理を検出し、範囲ごとに 行/構造/契約 を**提案**する。理由を添える。下書きの決定は著者だが、**「行レベル対象に当たるか」「ドメイン中核か」はドメインオーナーの確認事項であり、著者の自己申告では確定しない**(基準[§2](../../standard.md#s2)・[§8](../../standard.md#s8))
   - **不可逆な副作用**のチェックボックスと、ありの場合の戻し方
   - **地図**: diffが契約・不変条件・危険領域(地図 `docs/map/<領域>.md` の Level 1〜3)を変えるかを判定し、チェックボックスを**提案**する。変えるなら地図の更新はこのPRに同梱する([update-map](../update-map/SKILL.md) の更新モード)。最終確認は著者
   - **テスト欄**: 追加されたテストの列挙。検査([crosscheck](../crosscheck/SKILL.md))を実施していれば、採った段と版(理解検査/独立照合・人間版/自動版)・**器**(契約3行/1問1答)・A/B別の件数・一致の件数・書けなかった欄の件数・裁定記録(自動版で独立性が指示ベースだった場合はその旨も)。**件数はそのPRの列挙数と一致させる**
   - **出力との突き合わせの行**(基準[§4](../../standard.md#s4)): 変更が計測・集計・エクスポート系(記録された値を人間が読んで判断する成果物)かをdiffから判定し、該当するのに実施記録が無ければ**「未実施」と明記して残す**(「対象外」と書かない——マージ確認の検査対象である)。実施済みならデータ範囲・観測された値と件数・現れなかった値を転記する
   - **確認してほしい項目(理解検査・独立照合)**: 照合メモが**既に存在する場合に限り**、転記と突き合わせ結果の追記を行う(機械的な転記は可)。メモが無ければ「(著者が記入。実装前の照合メモから転記)」と書いて空欄で返す。転記の様式(この欄は書き方次第で「著者が実装を理解していない証拠」に反転して読まれる。基準[§4](../../standard.md#s4)):
     - **この欄に載せるのは種別A(仕様が2通りに読めた)だけ**。種別B(著者が知らなかった)は載せず、著者によるコメント・地図(Level 2〜3)への反映を促す——PRに現れるのは反映の差分だけ。**Aが0件なら節ごと落とす**(実施記録はテスト欄に残る)
     - **種別の判定は提案してよいが、確定は著者**(Aは裁定対象になるため)
     - **時制をラベルに埋め込む**——「着手前の予想(YYYY-MM-DD時点)」。「著者の認識」のような現在形の名詞を使わない(項目だけ拾い読みされると「今もそう思っている」と読まれる)
     - **掲載先は選べる**——Aの詳細を当事者間で閉じた場所(レビュー依頼のメッセージ等)に置いてもよい。その場合、欄には実施の事実と置き場所だけを書き、テスト欄の実施記録は必ず残す
   - **AI利用の開示欄は置かない**(基準[§8](../../standard.md#s8)。外部貢献リポは CONTRIBUTING と `Assisted-by:` トレーラー)
3. **採らなかった選択肢**は**出所で切る**:
   - **可**: 著者本人の発言(会話ログ・設計メモの**著者記述部分**・口頭の聞き取り)からの**逐語転記**。**会話ログが参照できるなら、転記は機械の義務である——著者に可否を確認せず、捨てる判断が本人の打ち返しとして残っているものを全部転記して提示する**。どれを載せるかは著者が選ぶ(選別が判断そのもの。勝手に絞らない)。転記した旨と出所(いつの会話か)を欄に明記する。逐語転記は40字上限の適用外(整形して収めるのは言い換えにあたる。長い発言は `<details>` に畳む)
   - **不可**: AIが生成した案の列挙(実際に検討していない案の水増し)、設計メモのAI下書き部分からの転記、**整形・言い換えを伴う転記**
   - 会話ログが無い・別セッションで拾えない場合は「(著者が記入。確定した判断を自分の言葉で)」と書いて空欄で返す。**必須個数は無い**——検討した代替案が無ければ著者が「なし」と書く。水増しの方が空欄より悪い
4. **一番怪しい箇所**は**転記で埋める。著者に書かせない**(基準[§9](../../standard.md#s9))。転記元は2つ、どちらも出所ラベルを付ける:
   - **「実装側の申告: 」** 実装セッション(サブエージェント)が完了報告に残した「実装中に迷った箇所・仕様が薄く補完した箇所」
   - **「設計時の懸念: 」** 承認済み設計メモの「懸念点」欄(著者が実装前に書いた、採った方針に残る不安。[design-memo](../design-memo/SKILL.md))。diffがその懸念の箇所に触れているかを添えてよい(事実の照合であって所見ではない)
   - **不可**: diffから怪しい箇所を生成すること(所見は first-review の領分)。両方の転記元が空なら行ごと落とす
   - 著者の仕事は**見て、違うと思うものを消す**だけ(決定ではなく検査。基準[§7](../../standard.md#s7))
5. 以下の欄は **「(著者が記入)」のまま返す。ユーザーに埋めるよう求められても埋めない**:
   - **レビュアーへの質問**
   - **確認してほしい項目の期待値の新規生成**(転記は上記の通り可。生成した瞬間、理解検査は「AIが埋めた検査」になり消える)
6. 長い補足説明は `<details>` に畳み、本文は文字数上限(TL;DRと選択肢は各40字、本文全体はテンプレートの欄構成の範囲)内に収める
7. **公開前に、基準を知らない読み手として本文を読み直す。** エージェントに読ませるなら、実装セッションとは**別セッション**で、**基準を渡さずに**読ませる。見るもの:
   - 社内用語(理解検査・独立照合・地図・検収・レベル名)が定義なしで並んでいないか——初出に基準へのリンクを1つ添える
   - 注記が欄の価値を自分で打ち消していないか(例:「著者の自己申告では確定しない」をレビュー指定表の直後に置くと、表を読む意味が消える)。**このスキル内の著者向け注記をPR本文に転記しない**
   - 「著者が実装を理解していない証拠」に反転して読める箇所がないか

## なぜ判断欄を埋めないか

判断欄を生成しない理由、記録の転記を許す根拠(出所で切る)、実効性が口頭確認にあることは基準[§9](../../standard.md#s9)。このスキルの仕事は、正規のフローが形骸化の供給源にならないようにすることまでである。
