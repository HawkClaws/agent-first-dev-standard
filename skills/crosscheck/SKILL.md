# 理解検査・独立照合(基準[§4](../../standard.md#s4)の実装)

> **このスキルは3つの段を持つ。** **標準は理解検査**(手順U)——著者が実装の出力を見る前に期待値を書く。**不可逆系には独立照合が必須**で、人間版(手順A)の書き手は**実装方針を書いていない人**(レビュアー/ドメインオーナー)、**自動版**(手順B)は重いときだけ。手順0でどれかを判定してから進む。
>
> **理解検査と人間版はテストを1本も生成しない。** 旧名 `gen-tests` は自動版だけを指していたので改名した。

同じセッションが実装とテストを書くと、検証ではなく自作自演になる(エージェントは実装に合わせたテストを書く)。レビューでも代替できない——レビュアーは実装を読んでからテストを読むので、読み方が「テストは実装と合っているか」に固定される。対抗手段は**実装の出力を見る前に書かれた期待値**であり、誰が書くかで検査の名前と強さが変わる:**著者が書けば理解検査(標準)、実装方針を書いていない人が書けば独立照合(不可逆系で必須)**。

## 手順0. 段と版を選ぶ

1. **不可逆系(スキーマ・データ移行・課金・外部送信・削除)か確認する。** 不可逆系なら**独立照合が必須**(手順AまたはB)。理解検査では代替できない——著者は自分の読みを自分で正解にできる(基準[§4](../../standard.md#s4))。
2. 不可逆系でなければ、構造理解以上の変更には**理解検査**(手順U)が標準。契約理解レベルは任意。第二解釈者を確保できるなら独立照合を足すのは引き続き推奨。
3. 独立照合をやる場合、次のどれかに当てはまれば**自動版**(手順B)、当てはまらなければ**人間版**(手順A)。判定理由を1行で示す。
   - 照合すべき契約が多く、人間の先読みが全件に回らない
   - 仕様が長い・入り組んでいて、読んでも期待値を書き出せない
   - 同種の変更で過去に裁定が発生した領域

## 共通:仕様の切り出し(汚染の遮断)

どちらの版でも、解釈のもとにするのは**実装前に書かれた仕様**だけである。

- 使うもの: チケット、承認済み設計メモの**要求・契約の記述部分**(契約を変える変更では、設計メモと一緒に承認された地図 Level 1 の契約記述。[design-memo](../design-memo/SKILL.md) 参照)、インターフェース定義(関数シグネチャ・型・API定義)
  - **ここが空なら、照合は成立しない。** 「仕様に記述なし」が全欄に並ぶ照合は実施ではない。材料が無いことを報告して、設計メモ側に戻す
- 使わないもの:
  - 実装後にAIに書かせた仕様サマリ・PR説明文(仕様を経由して自作自演が復活する)
  - **AI一次レビュー([first-review](../first-review/SKILL.md))の出力**——実装の挙動・行番号・欠陥を詳細に記述するので、実装コードを見せるのとほぼ同じ汚染になる。**first-review はこのスキルより前の段(PR作成)で走るため、これが一番踏みやすい経路である**
  - 設計メモの**方針・触る範囲**(=実装の設計図。実装側の解釈を先に共有すると「2回の独立解釈」が崩れる)
  - CLAUDE.md 等に埋め込まれたアーキテクチャ記述([update-map](../update-map/SKILL.md) 参照)

切り出した仕様とインターフェースを**そのまま引用して提示する**(要約するとこのスキル自身が解釈を1つ挟むことになる)。

**不変条件は「その状況が起きたらどうなるか」の問いに変換して出す。**「同じ注文が2回記録されないこと」のような不変条件は、そのままでは期待値の器に載らない(書き手がYes/No質問として読んでしまう)。「同じ注文について保存が2回走ったらどうなるか」「担当者が一覧をエクスポートしたとき、他テナントの行は入るか」のように変換すると、埋められる形になる。

## 手順U. 理解検査(標準・著者版)

検査対象は仕様の曖昧さではなく**著者の理解**(基準[§4](../../standard.md#s4))。著者は設計メモを書いた当事者なので独立解釈にはならないが、コードを書いたのはエージェントであり、設計メモに書かなかった細部では検出力が残る。**独立照合を名乗らない。**

1. **著者が契約を自分の言葉で言い直す。** 上で切り出した仕様とインターフェースをもとに、契約ごとに次の器(基準[§2](../../standard.md#s2)の契約3行)を著者自身が埋める。手順A-2の4欄は**使わない**——独立照合は第二解釈者が期待値を**生成**する足場として4欄が要るが、理解検査が求めるのは著者の理解の**出力**であり、「入力」のような抽象的な欄名は対象の言い換え(`入力: 上流サービスからの結果`)を誘発するだけである。

   ```
   - 契約: <契約名。仕様の言葉で。ここだけ機械が埋めてよい>
     - 成功したら:
     - 失敗したら:
     - 前提:
     - 仕様に書かれていない点: (任意)
   ```

   - **契約名は仕様の言葉で書く**(例:「レポート生成が成功したとき、何が残るか」)。実装側の語彙(クラス名・イベント名)で書くと、機械が埋めてよい唯一の欄が着手の障壁になり、検査全体が止まる。
   - **不変条件は「その状況が起きたらどうなるか」の問いに変換して出す**(共通節)。
   - 直接編集でも、**エージェントによる聞き取り**(手順A-2の聞き取り方式——1問ずつ質問し、答えをそのまま書き留める)でもよい。**実装の差分・テスト・first-review の出力を開く前に書く。** 理想は実装と並列——実装出力がまだ存在しない時点で書き終えていれば、汚染は起こりえない。
   - **選択式にするなら条件付き。** ①選択肢は**仕様から作る**(実装から作ると、実装から作った選択肢に○を付ける自作自演に戻る)②**「上のどれでもない」「わからない」を必ず入れる**(そこが選ばれること自体が検査結果)③選んだ後に**理由を1行だけ自分の言葉で**書く(再生の要素を残す)。理由なしの選択式のみで実施した場合は「理解検査」を名乗らず**「理解度チェック(選択式)」**と別表記する——再認(選べる)は再生(自分の言葉で言える)の代わりにならない(版表記と同じ規律)。
2. **書いた期待値をエージェントの入力に入れない。** 設計メモに書いてエージェントに読ませると、エージェントが期待値に合わせて実装し、一致が自動生成されて検査がトートロジーになる。照合メモは別ファイルに置き、実装セッションに渡さない。**聞き取り方式の場合、聞き取りをしたセッションに実装を委譲しない**(同じ理由)。
3. **書けない欄があったら、それが検査結果である。** 理解不足か仕様の曖昧さのシグナルとして記録し、仕様・設計メモに戻る。**エージェントに埋めさせた時点で検査は消える。**
4. **実装後に突き合わせる**(手順A-4と同じ)。一致・食い違い・仕様に記述なしに分類。食い違いの扱いは手順C(裁定)へ。
5. **表と結果をPRの「確認してほしい項目」欄に転記する**([pr-guide](../pr-guide/SKILL.md) のテンプレート)。レビュアーはこの表を起点に、著者の読みごと検証できる。
6. **成果指標は一致件数ではない。** 著者 vs エージェントでは一致して当然。成果は、書けなかった欄の数(理解の穴)・「仕様に記述なし」の数(仕様の穴)・食い違いの数(実装の逸脱)。

記録には「理解検査(著者)」と明記し、独立照合と混ぜない。

## 手順A. 人間版(不可逆系の既定)

**実行時期: 実装と並列。実装の完了を待たない。** 材料の提示と期待値の書き出しは、実装が始まる前か進行中にやる。理由は2つ——①クリティカルパスに乗らない(実測で0分)②**実装ファイルがまだ存在しないので、隔離が指示ではなく構成で保証される**。実装後に回すと、レビュアーがPRや first-review の出力を開いた時点で汚染される。突き合わせ(手順A-4)だけは実装ができてから。

**書き手は、実装方針を書いていない人である**(レビュアー。不可逆系ならドメインオーナー)。著者が書くと、実装の設計図を書いた当事者が第二解釈者を兼ねることになり、実施記録の付いた自己照合になる(基準[§4](../../standard.md#s4))。**誰に渡すかを最初に確認し、著者本人だった場合はその旨を記録に残す。**

1. **仕様面だけを出す。** 上で切り出した仕様とインターフェースを提示する。この出力に**実装コード・テストコード・実装の挙動説明・AI一次レビューの出力を一切含めない**。含めた時点でアンカーが実装側に移り、このスキルの意味が消える。
2. **期待値メモの器を渡す。** 契約ごとに次の箇条書きを出し、中身は埋めない。埋めるのは人間である。**Markdownの表は使わない**——人間が直接編集する欄に、編集の重い書式を要求しない。

   ```
   - 契約: <契約名。仕様の言葉で。ここだけ機械が埋めてよい>
     - 入力:
     - 期待する出力:
     - 失敗時の挙動:
     - 仕様に書かれていない点:
   ```

   **契約名は仕様の言葉で書く**(手順U-1と同じ)。実装側の語彙で書くと、書き手が「意味が分からない」で着手できない。

   **聞き取り方式でもよい。** 直接編集の代わりに、エージェントが契約ごとに上の4点を1問ずつ質問し、人間の答えをそのまま書き留める。**書き留めるのは転記であって生成ではない**——人間が言っていない期待値を、補完・整形の名目で足さない。答えられない欄は空欄のまま「書けなかった」と記録する(それ自体が結果である)。**聞き取り係は実装を書かないセッションにする**(答えを聞いたセッションが実装すると、期待値に合わせた実装になる)。

3. **人間が書き終える(答え終える)まで待つ。** ここで先回りして埋めてはいけない(自作自演になる)。書き出せない欄があったら、それは仕様が曖昧か理解が足りないシグナルとして記録する。
4. **突き合わせる。** 人間のメモを受け取ってから実装とテストを開き、メモの各行と実際の挙動を照合して、一致・食い違い・仕様に記述なしに分類する。
5. 手順C(裁定)へ。

## 手順B. 自動版(独立テスト生成)

1. **ファイル読み取り・検索ツールを持たないサブエージェント**を起動し、切り出した仕様とインターフェースだけを渡して「この仕様とインターフェースを満たすテストを書け」と指示する。
   - Claude Code なら `.claude/agents/` に Read / Grep / Glob / Bash を外したエージェント定義を置いて使う(例は下記)。プロンプトの「実装を読むな」は防壁ではない——動くテストを書くために設定や既存コードを読みに行く動機がサブエージェント側に常にある
   - ツール制限ができない環境では、リポジトリ外の素のチャット(可能なら**別ベンダーのモデル**。同じモデル同士は同じ読み間違いをしやすい)に仕様とインターフェースを貼って生成させる
   - 同一コンテキスト内で「サブエージェントのつもり」で書いてはいけない。実装が見えている時点でこのスキルの意味が消える
   - **「幅を持たせたアサーションを書くな」を明示的に指示する。** 期待値には素直な一つの値を書かせ、決められない箇所は**テストではなく「仕様に記述なし」のリスト**に出させる。これを言わないと、曖昧な箇所ほど許容範囲の広いアサーション(`expected - 1日分 <= result <= expected + 1` のような)になり、**曖昧さがアサーションの中に埋め込まれて、どちらの解釈でも緑になる**
2. 生成されたテストを実装に対して実行する。import パス等の**実行のための機械的修正**はよいが、**落ちたテストのアサーションや期待値を実装に合わせて直してはいけない**——落ちたテストは修正対象ではなく裁定対象である。
3. 結果を分類する。**通ったテスト** → 契約の固定として採用候補。**落ちたテスト** → 仕様のどの記述がどう曖昧だったかを特定して提示する。
4. 手順C(裁定)へ。

ツール制限付きエージェント定義の例(`.claude/agents/spec-test-writer.md`):

```markdown
---
name: spec-test-writer
description: 仕様とインターフェースだけからテストを書く。実装コードへのアクセスを持たない。
tools: []
---
渡された仕様とインターフェース定義だけを根拠にテストコードを書く。
実装の中身を推測で補完せず、仕様に書かれていない挙動には
「仕様に記述なし」とコメントを付けてテスト対象から外すか、素直な解釈で書く。
```

## 手順C. 裁定(両版共通)

1. 食い違いを**バグ報告としてではなく「仕様が2通りに読めた証拠」として**提示する。仕様のどの記述が、どう2通りに読めたかを名指しする。
2. **どちらの解釈が意図かを決めるのは仕様の持ち主(人間)。** 仕様の持ち主が著者本人の場合、不可逆系の裁定にはドメインオーナーを加える(自分の解釈を自分で正解にできてしまう)。
3. 裁定結果を**書き戻す。書き戻し先は3つある**(基準[§4](../../standard.md#s4)):
   - **仕様・設計メモ** — コードだけ直して仕様を放置すると、次の変更で同じ食い違いが再発する
   - **裁定前に書かれたテスト** — 実装と同じセッションが書いたテストは裁定前の読みを固定している。放置すると**間違った読みが「守るべき回帰」として保護される**
   - **地図(Level 1〜2)** — 契約・不変条件を変えた場合。次回の独立照合が参照する「実装前に書かれた記述」になる
4. PRのテスト欄に、採った版(人間版/自動版)・食い違いの件数・裁定内容を記録する([pr-guide](../pr-guide/SKILL.md))。

## 守ること

- **人間版で最も壊れやすいのは手順A-1である。** 実装やテストの中身を1行でも先に見せたら、その後にどれだけ丁寧に期待値を書いても独立照合ではない。
- **書き手がPRを開く順序を守る。** 期待値を書き終わるまで、PRの差分・テスト・AI一次レビューの出力を読まない。**フロー上 first-review はこのスキルより前に走るので、レビュアーが普通にPRを開くと汚染される。** 期待値の書き出しは**実装と並列**に済ませる——実装がまだ存在しない時点で終わっていれば、汚染は起こりえない。
- **人間版は、実施したことを機械検査できない。** 期待値を先に書いたか、テストを見てから書いたかは自己申告でしか分からない。自動版はツール使用ログで隔離を確認できるので、**確認できる環境ではサブエージェントのツール使用ログに実装ファイルへのアクセスがないことを確認する**。ツール制限なし・ログ確認なしで自動版を実施した場合は、裁定記録に「独立性は指示ベース」と明記する(「独立検証済み」のラベルが実態より強く読まれるのを防ぐ)。
- **自動版の主な失敗は赤の見逃しではなく、曖昧さの吸収である。** 曖昧な箇所に幅を持たせたアサーションを書くと、検出力がゼロになったまま「24件すべて緑」という強い見た目の結果が出る。**緑の件数は独立照合の成果ではない。** 成果は食い違いの件数と「仕様に記述なし」の件数である。
- **2つの解釈が同じ読み間違いで一致した場合、食い違いは出ない。** 食い違いは検出できるが、**一致の正しさは保証されない**。最後に著者へ「自分で追加のエッジケースを1〜2個考える」ことを促して終える。
- **両版をやる必要はない。** 必須なのは独立照合であって、自動版ではない(基準[§4](../../standard.md#s4))。人間版だけで通した場合に「独立照合なし」と扱われないよう、記録には版を明記する。
