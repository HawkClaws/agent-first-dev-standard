# 独立照合

> **このスキルは不可逆系のためのものである。** 書き手は**実装方針を書いていない人**(レビュアー/ドメインオーナー。手順A)か、**実装を見せないツール制限サブエージェント**(手順B)。手順0で版を判定してから進む。
>
> **不可逆系でない変更に、実装後の突き合わせは置かない。** 標準の検査は着手時の**設計の聞き取り**([design-memo](../design-memo/SKILL.md))と、PR確認時の**メモ外の決定の仕分け**([flow](../flow/SKILL.md) 停止2)である。著者が自分の期待値を書いて自分の委譲した実装と突き合わせても、期待値は委譲プロンプトに入っているので一致は自動生成される——検査ではなくトートロジーになる。
>
> **人間版はテストを1本も生成しない**(結合テスト仕様書が要るときだけ手順Bで仕様書を足し、記録に併記する——手順0-4)。

対抗手段は**実装の出力を見る前に、実装方針を書いていない人(または実装を見せないセッション)が書いた期待値**である。

## 手順0. 段と版を選ぶ

1. **不可逆系(スキーマ変更・データ移行・課金・外部送信・削除)か確認する。** 不可逆系なら**独立照合が必須**(手順AまたはB)。著者の聞き取りでは代替できない——著者は自分の読みを自分で正解にできる。
2. 不可逆系でなければ、このスキルの対象外(`[-]`)。標準の検査は設計の聞き取りとメモ外の決定の仕分け(上記)。第二解釈者を確保できるなら独立照合を足すのは引き続き推奨。
3. 独立照合をやる場合、次のどれかに当てはまれば**自動版**(手順B)、当てはまらなければ**人間版**(手順A)。判定理由を1行で示す。
   - 照合すべき契約が多く、人間の先読みが全件に回らない
   - 仕様が長い・入り組んでいて、読んでも期待値を書き出せない
   - 同種の変更で過去に裁定が発生した領域
   - **第二解釈者を確保できない(一人運用)。** 不可逆系の独立照合は省略できないので自動版で満たす。可能なら別ベンダーのモデルを使い、記録に「第二解釈者不在のため自動版」と残す
4. **結合テスト仕様書が要る場合**(flow のヘッダ: 自動の実行手段が無い境界を人が確認する・納品・監査)は、**段に関係なく**手順Bで仕様書を生成する。人間版と併用したときの記録は「人間版+結合テスト仕様書」のように併記する。人間版の期待値メモは実行手順を持たないので、仕様書は手順Bでしか出ない

## 共通:仕様の切り出し(汚染の遮断)

どちらの版でも、解釈のもとにするのは**実装前に書かれた仕様**だけである。

- 使うもの: チケット、承認済み設計メモの**要求・契約の記述部分**(契約を変える変更では設計メモの「契約」欄。在り処と承認の記録は flow の状態ファイルのヘッダ。[design-memo](../design-memo/SKILL.md)「出力の置き場所」参照)、**既存の地図 Level 1**(前回までの実装済みの契約=現実の記述。今回の変更の意図は書かれていないので、変えない契約の期待値にだけ使う)、インターフェース定義(関数シグネチャ・型・API定義)
  - **ここが空なら、照合は成立しない。** 「仕様に記述なし」が全欄に並ぶ照合は実施ではない。材料が無いことを報告して、設計メモ側に戻す
- 使わないもの:
  - 実装後にAIに書かせた仕様サマリ・PR説明文(仕様を経由して自作自演が復活する)
  - **AI一次レビュー([first-review](../first-review/SKILL.md))の出力**——実装の挙動・行番号・欠陥を詳細に記述するので、実装コードを見せるのとほぼ同じ汚染になる。踏みやすい経路は「守ること」
  - 設計メモの**方針・触る範囲・聞き取りの記録**(=実装の設計図。設計メモは聞き取りで厚くなっているので、渡すのは「契約」欄と要求の記述だけと決める。実装側の解釈を先に共有すると「2回の独立解釈」が崩れる)
  - CLAUDE.md 等に埋め込まれたアーキテクチャ記述([update-map](../update-map/SKILL.md) 参照)

切り出した仕様とインターフェースを**そのまま引用して提示する**(要約するとこのスキル自身が解釈を1つ挟むことになる)。

**不変条件は「その状況が起きたらどうなるか」の問いに変換して出す。**「同じ注文が2回記録されないこと」「他テナントのデータは見えないこと」のような不変条件は、そのままでは期待値の器に載らない。「同じ注文について保存が2回走ったらどうなるか」「担当者が一覧をエクスポートしたとき、他テナントの行は**どう扱われるか**」のように変換する。**Yes/Noで答えられる形にしない**(「〜は入るか」で閉じると元のYes/No質問に戻る)。**「どうなるか」「何が起きるか」「どう扱われるか」で開く。**

## 手順A. 人間版(不可逆系の既定)

**実行時期: 実装と並列。** 実装の完了を待たない。突き合わせ(手順A-4)だけは実装後。

**書き手は実装方針を書いていない人**(レビュアー。不可逆系ならドメインオーナー)。著者が書いたものは独立照合として記録しない(一人運用なら手順Bへ)。

1. **仕様面だけを出す。** 上で切り出した仕様とインターフェースを提示する。この出力に**実装コード・テストコード・実装の挙動説明・AI一次レビューの出力を一切含めない**。含めた時点でアンカーが実装側に移り、このスキルの意味が消える。
2. **期待値メモの器を渡す。** 契約ごとに次の箇条書きを出し、中身は埋めない。埋めるのは人間である。**Markdownの表は使わない**——人間が直接編集する欄に、編集の重い書式を要求しない。

   ```
   - 契約: <契約名。仕様の言葉で。ここだけ機械が埋めてよい>
     - 入力:
     - 期待する出力:
     - 失敗時の挙動:
     - 仕様に書かれていない点:
   ```

   **聞き取り方式でもよい。** 直接編集の代わりに、エージェントが契約ごとに上の4点を1問ずつ質問し、第二解釈者の答えをそのまま書き留める。**設計の聞き取りと違い、推奨回答を添えない**——機械の読みを渡した時点で、第二解釈者の解釈は実装を経由していない独立な解釈ではなくなる。**書き留めるのは転記であって生成ではない**——人間が言っていない期待値を、補完・整形の名目で足さない。答えられない欄は空欄のまま「書けなかった」と記録する(それ自体が結果である)。

3. **人間が書き終える(答え終える)まで待つ。** ここで先回りして埋めてはいけない(自作自演になる)。書き出せない欄があったら、それは仕様が曖昧か理解が足りないシグナルとして記録する。
4. **突き合わせる。** 人間のメモを受け取ってから実装とテストを開き、メモの各行と実際の挙動を照合して、一致・食い違い・仕様に記述なしに分類する。
5. 手順C(裁定)へ。

## 手順B. 自動版(独立テスト生成)

1. **ファイル読み取り・検索ツールを持たないサブエージェント**を起動し、切り出した仕様とインターフェースだけを渡して「この仕様とインターフェースを満たすテストを書け」と指示する。**生成は実装の完了を待たない**——flow では委譲の直後に起動する(実装がまだ無い時点なら隔離は構成で保証される)。実行だけが実装後。例外は、完了報告で初めて「固定しなかった境界」が分かった場合の**追加生成**——同じツール制限で、渡すのは着手時に切り出した引用と同じもの(完了報告・diff の内容を材料に混ぜない)。
   - **出力形式を境界ごとに先に決める。** 既定はテストコード。**自動の実行手段が無い境界**(flow のヘッダで実行手段が「なし」)と、**文書としての納品・監査が要る場合**(著者の申告。flow のヘッダ)は**結合テスト仕様書**。**不可逆系の境界は、人が実物相当で確認できる場合にだけ仕様書にできる**(「実物相当なし」の境界は人も実行できない)。仕様書の器は次の5点を項目ごとに書かせる(Markdown の表は使わない——人が実行しながら結果を書き込む欄になる)。期待結果に幅を持たせない規律はコードと同じで、決められない箇所は「仕様に記述なし」に出す

     ```
     - 試験項目: <仕様の言葉で。越える境界名を添える>
       - 前提と入力:
       - 手順:
       - 期待結果: <素直な一つの値・状態>
       - 仕様の根拠: <引用>
       - 仕様に記述なし: (任意)
       - 観測: (人が実行して見た値・状態をそのまま。一致/食い違いより先に書く)
       - 結果: 一致 / 食い違い / 実行できず(理由)
     ```

   - Claude Code なら `.claude/agents/` に Read / Grep / Glob / Bash を外したエージェント定義を置いて使う(例は下記)。プロンプトの「実装を読むな」は防壁ではない
   - ツール制限ができない環境では、リポジトリ外の素のチャット(可能なら**別ベンダーのモデル**。同じモデル同士は同じ読み間違いをしやすい)に仕様とインターフェースを貼って生成させる
   - 同一コンテキスト内で「サブエージェントのつもり」で書いてはいけない。実装が見えている時点でこのスキルの意味が消える
   - **「幅を持たせたアサーションを書くな」を明示的に指示する。** 期待値には素直な一つの値を書かせ、決められない箇所は**テストではなく「仕様に記述なし」のリスト**に出させる。これを言わないと、曖昧な箇所ほど許容範囲の広いアサーションになり、**曖昧さがアサーションの中に埋め込まれて、どちらの解釈でも緑になる**
2. 生成されたテストを実装に対して実行する。import パス等の**実行のための機械的修正**はよいが、**落ちたテストのアサーションや期待値を実装に合わせて直してはいけない**——落ちたテストは修正対象ではなく裁定対象である。**結合テスト仕様書は人(著者)が実行し**、項目ごとに「観測」を書いてから「結果」を書く(生成は機械、実行と記入は人、裁定は人。観測の記入は作業から得られる知識の申告、一致/食い違いは観測と期待結果の比較——**観測を書かずに一致と書かない**。著者は一致判定の当事者なので、第三者が観測から検証できる形で残す)。実行先はヘッダの実物相当(サンドボックス・テスト用テナント・検証環境)。**不可逆系の境界を本番に通して確認しない**——人が実行しても同じ。実行できなかった項目は「実行できず」と理由を残す——一致に丸めない。**全項目が「実行できず」なら照合は実施ではない**——「未実施(実行先なし)」と記録し、独立照合を満たしたことにしない。生成された仕様書は書き換えず、観測と結果の欄だけを追記する——期待結果を変えるのは裁定の書き戻し(追記)だけ。置き場所は照合メモと同じ(リポジトリの外、委譲プロンプトに現れるどのパスの祖先でもない場所)。納品する場合も生成時の版を残す
3. 結果を分類する。**通ったテスト** → 契約の固定として採用候補。**落ちたテスト** → 仕様のどの記述がどう曖昧だったかを特定して提示する。仕様書なら一致/食い違いを同じに扱う。ただし**仕様書は回帰を固定しない**(手動の実行で守れるのは実行した経路だけ)——一致した項目は、実行手段が整った境界からテストコードに移す候補として残す。納品・監査に出すのは裁定の書き戻し後の版で、**確認しなかった境界・経路を末尾に列挙し、網羅を主張しない**(一致の件数は実行した項目の数であって、境界の網羅ではない)
4. 手順C(裁定)へ。

ツール制限付きエージェント定義の例(`.claude/agents/spec-test-writer.md`):

```markdown
---
name: spec-test-writer
description: 仕様とインターフェースだけからテスト(コード、または結合テスト仕様書)を書く。実装コードへのアクセスを持たない。
tools: []
---
渡された仕様とインターフェース定義だけを根拠に、指示された形式(テストコード、または結合テスト仕様書)でテストを書く。
実装の中身を推測で補完せず、仕様に書かれていない挙動には
「仕様に記述なし」とコメントを付けてテスト対象から外すか、素直な解釈で書く。
```

## 手順C. 裁定(両版共通)

1. 食い違いを**バグ報告としてではなく「仕様が2通りに読めた証拠」として**提示する。仕様のどの記述が、どう2通りに読めたかを名指しする。
2. **どちらの解釈が意図かを決めるのは仕様の持ち主(人間)。** 仕様の持ち主が著者本人の場合、不可逆系の裁定にはドメインオーナーを加える(自分の解釈を自分で正解にできてしまう)。
3. 裁定結果を**書き戻す。書き戻し先は3つある**:
   - **仕様・設計メモ** — コードだけ直して仕様を放置すると、次の変更で同じ食い違いが再発する
   - **裁定前に書かれたテスト(テストコードと結合テスト仕様書)** — 実装と同じセッションが書いたテストは裁定前の読みを固定している。仕様書は納品・監査に出るなら必ず。放置すると**間違った読みが「守るべき回帰」として保護される**
   - **地図(Level 1〜2)** — 契約・不変条件を変えた場合。次回の独立照合が参照する「実装前に書かれた記述」になる
4. 食い違いはPRの「確認してほしい項目」欄へ、実施記録(採った版(人間版/自動版)・食い違いの件数・裁定内容)はテスト欄に記録する([pr-guide](../pr-guide/SKILL.md))。メモ外の決定で「裁定へ」に仕分けられたもの([flow](../flow/SKILL.md) 停止2)もこの手順で裁く。

## 守ること

- **メモ外の決定の仕分けは、著者が first-review の出力を開く前に行う**(flow 停止2の提示順)。first-review の所見は実装の挙動を詳述するため、先に読むと「実装は筋が通っている=受け入れ」に倒れやすく、差し戻しと裁定が発火しなくなる。この順序は構成では守れない指示ベースの規律なので、仕分けの記録を済ませてから開く。
- **人間版で最も壊れやすいのは手順A-1である。** 実装やテストの中身を1行でも先に見せたら独立照合ではない。書き手は期待値を書き終わるまでPRの差分・テスト・AI一次レビューの出力を読まない(first-review はレビュー段より前に走るので、第二解釈者が普通にPRを開くと汚染される)。
- 自動版は、サブエージェントのツール使用ログに実装ファイルへのアクセスがないことを確認する。ツール制限なし・ログ確認なしなら裁定記録に「独立性は指示ベース」と明記する。
- 突き合わせが終わった後、著者に追加のエッジケースを1〜2個考えるよう促して終える。
