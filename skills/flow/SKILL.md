# フローの進行(基準の実行係)

**このスキルは規範を持たない。** 既存の5本(design-memo / crosscheck / pr-guide / first-review / update-map)を、基準が定めた順序で呼び、状態を1つのファイルに記録するだけである。判断は一切しない。

目的は摩擦を下げること。**スキルを1本ずつ手で呼ぶ運用は、忙しい日に最初に消える。**

## 状態ファイル

`docs/flow/<TICKET-ID>.md`。無ければ [assets/flow-template.md](assets/flow-template.md) からコピーして作る。
**テンプレートには基準へのリンクを張らない**(コピー先が `docs/flow/` なので相対パスが切れる)。`§4` のような平文で参照する。

このファイルの `👤` 付き項目の一覧が、**このチケットにおけるHuman-in-the-Loopの定義そのもの**である(基準[§7](../../standard.md#s7)・skills/README)。

## 手順

1. **状態ファイルを読む**(無ければ作る)。引数にチケットIDが無ければ、`docs/flow/` の中で未完了のものを提示して選ばせる
2. 上から見て、**最初の未チェック項目**へ進む
3. その項目が `👤` **でない**なら実行する:
   - 対応するスキルの手順に従う(スキルを持たない工程は基準本文の該当節に従う)
   - 終わったら `[x]` にし、**実測表に所要を1行追記**する
   - 次の項目へ。`👤` に当たるまでこれを繰り返す
4. その項目が `👤` なら**止まる**。次の形式で報告して終わる:
   - **何が必要か**(1行)
   - **誰が**(役割名。基準[§8](../../standard.md#s8)の割り当てに従う)
   - **なぜ機械で埋められないのか**(1行)
   - **判断材料**(ここまでに生成した下書きのパス)
   - **人間が埋めたら、もう一度このスキルを呼べば続きが走ること**
5. 状態ファイルのヘッダ(不可逆系・理解レベル・最終更新・次にやること)を更新して終わる

## 絶対にやらないこと

- **`👤` の項目にチェックを入れない。** 埋めることもしない。ここが空欄であることがこのフローの設計である
- **不可逆系のゲートで「期限まで無返事なら進む」をしない。** 明示的な承認が出るまで止まる(基準[§7](../../standard.md#s7))
- **設計メモの合意より前に実装を走らせない。** 順序は状態ファイルの並びのとおり
- **`👤` の項目を「不要」と判断して `[~]` にしない。** スキップの判断も人間のものである
- **「既に済んでいる」項目を `[~]` にしない。** `[x]` にして根拠(ファイルパス等)を書く。スキップ表は「重すぎた/不要だった/やる気がなかった」を溜める場所であり、そこに「既に済んでいる」を混ぜると[§12](../../standard.md#s12)の削除判断の材料が汚れる
- **領域を勝手に決めない。** 領域の切り方は地図の検収先・マージゲートの発効単位・境界をまたぐ契約の持ち主を決めてしまうので、`👤` である
- **マージ・プッシュ・デプロイをしない。** マージの決断は `👤` であり、その先の操作も人間が行う

## スキップの扱い

不要な工程は `[ ]` → `[~]` にし、**理由を「スキップした項目と理由」表に書く**。削除はしない。

理由は「重すぎた / 不要だった / やる気がなかった」のどれかに寄せて書く。これは基準[§12](../../standard.md#s12)の削除手続き
(a)「守られない原因の確認(コストなのか動機なのか)」の材料になる。**この表が溜まらないと、
重すぎる項目を削る根拠が永久に手に入らない。**

## 呼ばれ方

`/flow TICKET-201` のように呼ぶ。1チケットにつき、**人間のゲートの数だけ**呼べばよい
(現在の状態ファイルでは最大8回。スキルを1本ずつ呼ぶと15回以上になる)。

自動で連続実行させたくなるが、`👤` を跨いで自動進行させてはいけない。特に不可逆系では、
承認を待たずに実装が走ることになる。**待ちを消すのではなく、待ちの回数を減らすのがこのスキルの役割である。**

## 守ること

- **状態ファイルは作業中の道具であり、成果物ではない。** チケットが閉じたら消すか、実測表だけを残す。
  200行を超えたら記録が肥大している(基準[§11](../../standard.md#s11)の地図と同じ理由——読まれない記録は負債である)
- 実測の追記を省略しない。**このフローを回した記録だけが、基準を削る根拠になる**(基準[§12](../../standard.md#s12))
- 状態ファイルに設計判断や仕様を書かない。仕様はチケット、契約は地図、判断は設計メモとPRに置く。
  ここは進行状況だけを持つ
