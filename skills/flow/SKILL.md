# フローの進行(基準の実行係)

**このスキルは規範を持たない。** 既存の5本(design-memo / crosscheck / pr-guide / first-review / update-map)を、基準が定めた順序で呼び、状態を1つのファイルに記録するだけである。判断は一切しない。

## 状態ファイル

**リポジトリの外**の状態ディレクトリ `~/.flow/<リポジトリ名>/` に `<TICKET-ID>.md` を置く。無ければ [assets/flow-template.md](assets/flow-template.md) からコピーして作る(リポ外に置く根拠は CHANGELOG v0.32)。テンプレートには基準へのリンクを張らない(コピー先で相対パスが切れる)。`§4` のような平文で参照する。

このファイルの `👤` 付き項目の一覧が、**このチケットにおけるHuman-in-the-Loopの定義そのもの**である(基準[§7](../../standard.md#s7)・skills/README)。

## 手順

1. **チケットの本文を手に入れる。** この基準はチケットの置き場所を規定していない(Issue・Jira・Notion・リポジトリ内のファイル、どれでもよい)。
   - 引数に本文かその在り処(URL・パス・Issue番号)が渡されていればそれを使い、**在り処を状態ファイルのヘッダに書く**(2回目以降はここから辿る。毎回人間に聞き直さない)
   - 引数にもヘッダにも無ければ**ユーザーに聞く。推測で進めない**——薄いチケットを勝手に補完すると、著者の解釈が仕様に化ける(基準[§4](../../standard.md#s4))。薄いこと自体は設計メモの「未解決の論点」に出す
2. **状態ファイルを読む**(無ければ作る)。引数にIDが無ければ、状態ディレクトリの未完了のものを提示して選ばせる。ヘッダに「👤で止めた時刻」があれば、今の時刻との差を実測表の「人間の待ち」に書く(**経過時間であって作業時間ではない**——備考にそう書く)
3. 上から見て、**最初の未チェック項目**へ進む
4. その項目が `👤` **でない**なら実行する:
   - 対応するスキルの手順に従う(スキルを持たない工程は基準本文の該当節に従う)
   - **工程の前後に `date +%s` を実行し、差から所要(分)を実測表に1行追記する。推定で分を書かない**——この表が基準を削る根拠(§12)になる。測っていない数字は書けない
   - 判定(crosscheck 手順0 等)で対象外になった後続項目は `[-]`(対象外)にして根拠を1語添える。これは判定の帰結であって、`👤` のスキップではない
   - 次の項目へ。`👤` に当たるまでこれを繰り返す
5. その項目が `👤` なら**止まる**(既定。その場で聞き取り〔crosscheck 手順U・A-2、design-memo 手順4〕を始めるのは、**人間がその場で求めたときだけ**)。次の形式で報告して終わる:
   - **現在地**(固定書式。必ず先頭に):
     ```
     現在地: <段の列。済んだ段に ✅、いま止まっている位置に ◀ と👤の名前>
     進み:   完了 <n> / 全 <m> 項目(👤 は <i> / <j> 通過)。[-][~] は分母から除く
     未マージ: <`git branch --no-merged <切り元>` の出力をそのまま。切り元が未記録なら行を省く>
     この後: 機械が止まらずに走る工程 <k> 件(内訳)。見込み 約 <下限>〜<上限> 分(根拠: 本チケット実測 / 初期値)
     残りの 👤: <残数と名前の列>
     ```
   - **何が必要か**(1行)/**誰が**(役割名。基準[§8](../../standard.md#s8))/**なぜ機械で埋められないのか**(1行)/**判断材料**(ここまでに生成した下書きのパス)/**人間が埋めたら、もう一度このスキルを呼べば続きが走ること**
   - ヘッダの「👤で止めた時刻」に `date` の出力を書く
6. 状態ファイルのヘッダ(チケットの在り処・不可逆系・理解レベル・実装の委譲先・最終更新・次にやること)を更新して終わる

## 見込み(現在地の1行に使う)

- 参照値は**本チケットの実測**、無ければ下の初期値。下限=合計、上限=その2倍
- 初期値(分。出典: 基準を1周回した記録 TICKET-143——**1回の実測・架空題材**。自分の実測がたまったら使わない): 設計メモ系 1 / 検査の判定と材料の切り出し 1 / **実装の完了確認 4** / 自動版 3 / 地図の初版 1 / 突き合わせ・書き戻し 2 / PR下書き・地図同梱 1 / first-review 6 / 欄の検査・記録 1
- **実装の完了確認だけは規模に比例し、上限が無い。** 委譲時にサブエージェントへ「変更するファイル数と見込み(分)」を最初に報告させ、ヘッダの委譲先の行に書く
- **待ちの監視はしない**(待っている最中の flow は時計を見られない)。次に呼ばれたとき、ヘッダの時刻から経過を計算し、委譲の見込み上限(無ければ30分)を超えていたら現在地に「上限超過(<分>)」を1行出し、実測表にも残す(§12 の材料。初期値を直す根拠になる)

## セッションの分離(汚染の構成的防止)

人間と対話できるのは、このスキルを実行しているメインセッションだけである。したがって:

- **聞き取り(crosscheck 手順U・A-2)はメインセッションが行う。** 別セッションには置けない
- **同時進行の判定機構は持たない。** v0.30〜34 の作業ツリー検査と親ファイル `_active.md` は削除した——git の観測値から「マージ済みか・実装中か」を判定する機構は、git 運用の前提(未追跡ゼロ・既定ブランチ・マージ方式)を必ずどれか決め打ちし、実測で誤り続けた。squash / rebase マージでは v0.34 の消去条件が永久に偽になる(CHANGELOG v0.35)。「未マージのチケットがある間、同じ作業ツリーへ次の委譲をしない」は README の運用規約であり、flow は守らせない。代わりに**止まって報告するたび、現在地に「未マージ:」の1行を写す**(上の固定書式)。判定しない・消さない・これを理由に止まらない。マージ済みに見えるブランチが残る運用(squash 等)で行を掃除するのは人間の `git branch -D` である
- **人間が実装の並列を明示的に選んだ場合のみ**、`git worktree add <パス> -b <ブランチ> <切り元>` で専用の作業ツリーを作ってから委譲する(切り元が申告ではなく実行になる)。未追跡ファイル(.env 等)と依存物(venv・node_modules)は worktree に来ないことを委譲プロンプトに明記する。マージ後の `git worktree remove` は人間が行う
- **実装はサブエージェント(別セッション)に委譲する。** 委譲プロンプトにはチケットと承認済み設計メモの所在だけを含め、**照合メモの内容もパスも含めない**。**作業ブランチ(名前と切り元)と完了報告の置き場所(状態ディレクトリ配下の別ファイル)を指定し、ヘッダの「実装の委譲先」に書く**——次の呼び出しはここから「実装の完了確認」を行う。完了報告には「実装中に迷った箇所・仕様が薄く補完した箇所」を残させる(著者が実装の完了確認で読む。将来も参照したい事実は地図かコードコメントへ——基準[§9](../../standard.md#s9))
- **委譲は期待値の書き出し(聞き取り)より先に行い、完了を待たずに次の項目へ進む。** 委譲プロンプトを書いた時点で期待値がまだ存在しなければ、「渡さない」が指示ではなく構成で保証され、実装と聞き取りが並列に進む(基準§4「実装と並列」の実現機構)。順序が逆になった場合は、状態ファイルに**「独立性は指示ベース」**と記録する
- **照合メモはリポジトリの外に置く**(状態ディレクトリ配下でよいが、**別ファイル**にする——状態ファイルの所在は委譲プロンプトに書きうる)。リポ内に置くと実装サブエージェントの探索が届き、「渡さない」が構成で保証されない
- **first-review も実装とは別セッション(サブエージェント)で実行する**(基準§7)

## 絶対にやらないこと

- **`👤` の項目にチェックを入れない。埋めない。「不要」と判断して `[~]` にもしない。** スキップの判断も人間のものである。ここが空欄であることがこのフローの設計である(※判定で対象外になった `👤`——独立照合をやらないチケットの「独立照合の期待値」等——を `[-]` にするのは判定の帰結であり、これに当たらない)
- **不可逆系のゲートで「期限まで無返事なら進む」をしない**(明示的な承認まで止まる。基準[§7](../../standard.md#s7))。**設計メモの合意より前に実装を走らせない**
- **「既に済んでいる」項目を `[~]` にしない。** `[x]` にして根拠(ファイルパス等)を書く(スキップ表を汚さない。基準[§12](../../standard.md#s12))
- **領域を勝手に決めない**(`👤`)。例外は、どう切っても検収先・境界の持ち主が変わらない場合(一人運用など)——機械が決め、根拠と「機械が決めた」を状態ファイルに明記し、人の検査に回す(基準[§7](../../standard.md#s7))。切り方は基準[§11](../../standard.md#s11)
- **地図の初版を「このチケットのスコープを超える」を理由に別チケットへ先送りしない**(基準[§12](../../standard.md#s12) 手順2)
- **出力との突き合わせで、実データの所在が分からないまま進めない。** `👤` ではない止まり方(現在地+選べる手)で所在を聞く。**代表データを自作しない**——それは§4がこの工程で検出しようとした欠陥の再生産である
- **マージ・プッシュ・デプロイをしない。** マージの決断は `👤` であり、その先の操作も人間が行う

## スキップの扱い

不要な工程は `[ ]` → `[~]` にし、**理由を「スキップした項目と理由」表に書く**(重すぎた / 不要だった / やる気がなかった、のどれかに寄せる。基準[§12](../../standard.md#s12) 削除手続きの材料)。削除はしない。`[-]`(対象外)はスキップではないので表に書かない——根拠は項目の行に残っている。

## 呼ばれ方

`/flow TICKET-201 <チケットの本文かURL/パス>` のように呼ぶ(2回目以降はIDだけでよい——本文はヘッダの在り処から辿る)。1チケットにつき、**人間のゲートで止まる回数だけ**呼べばよい。マージの `👤` で止まった時点で機械の記録は終わっており、マージ後に呼び直す必要はない。

## 守ること

- **状態ファイルは作業中の道具であり、成果物ではない。** チケットが閉じたら人間が消すか、実測表だけを残す。200行を超えたら記録が肥大している
- 実測の追記を省略しない。**このフローを回した記録だけが、基準を削る根拠になる**(基準[§12](../../standard.md#s12))
- **他チケットと同時に進めているなら、実測表の備考に「同時進行: <ID群> / 実装順: n番目(決めた者)」を残す**(並行と直列の実測を分けて集計するため)。見込みの参照値を取るときは、同時進行の有無が同じ行を優先する
- **著者がエージェントの実装を手で書き換えた箇所があれば、実測表に1行残す**:「手書き: 疑った項目(基準§8 の①指示/②文脈/③設計/④タスクの切り方/⑤役割分割)と、直した手順書(無ければ「未修正」)」。手書き自体は禁止しない。**記録の無い手書きだけが、手順書の欠陥を次の人に隠す**(基準[§8](../../standard.md#s8))
- 状態ファイルに設計判断や仕様を書かない。仕様はチケット、契約は地図、判断は設計メモとPRに置く。ここは進行状況だけを持つ
