# フローの進行(基準の実行係)

**このスキルは規範を持たない。** 既存の5本(design-memo / crosscheck / pr-guide / first-review / update-map)を、基準が定めた順序で呼び、状態を1つのファイルに記録するだけである。判断は一切しない。

## 状態ファイル

**リポジトリの外**の状態ディレクトリ `~/.flow/<リポジトリ名>/` に `<TICKET-ID>.md` を置く。無ければ [assets/flow-template.md](assets/flow-template.md) からコピーして作る(リポ外に置く根拠は CHANGELOG v0.32)。テンプレートにもスキル本文にも、基準へのリンク・§番号は書かない(コピー先では辿れず、利用者には意味を持たない。保守者の索引は配布物に載せない)。

このファイルの `👤` 付き項目の一覧が、**このチケットにおけるHuman-in-the-Loopの定義そのもの**である。

## 手順

1. **チケットの本文を手に入れる。** この基準はチケットの置き場所を規定していない(Issue・Jira・Notion・リポジトリ内のファイル、どれでもよい)。
   - 引数に本文かその在り処(URL・パス・Issue番号)が渡されていればそれを使い、**在り処を状態ファイルのヘッダに書く**(2回目以降はここから辿る。毎回人間に聞き直さない)
   - 引数にもヘッダにも無ければ**ユーザーに聞く。推測で進めない**——薄いチケットを勝手に補完すると、著者の解釈が仕様に化ける。薄いこと自体は設計メモの「未解決の論点」に出す
2. **状態ファイルを読む**(無ければ作る)。引数にIDが無ければ、状態ディレクトリの未完了のものを提示して選ばせる。ヘッダに「👤で止めた時刻」があれば、今の時刻との差を実測表の「人間の待ち」に書く(**経過時間であって作業時間ではない**——備考にそう書く)
3. 上から見て、**最初の未チェック項目**へ進む
4. その項目が `👤` **でない**なら実行する:
   - 対応するスキルの手順に従う(スキルを持たない工程は基準本文の該当節に従う)
   - **工程の前後に `date +%s` を実行し、差から所要(分)を実測表に1行追記する。推定で分を書かない**——この表が基準を削る根拠になる。測っていない数字は書けない
   - 判定(crosscheck 手順0 等)で対象外になった後続項目は `[-]`(対象外)にして根拠を1語添える。これは判定の帰結であって、`👤` のスキップではない
   - 次の項目へ。`👤` に当たるまでこれを繰り返す
5. その項目が `👤` なら、**どの止まり方かをテンプレートの区分で決める**:
   - **停止1・停止2に属する `👤`**: 止まって人間を待つのではなく、**その停止の中で順に聞き取る**(crosscheck 手順U・A-2、design-memo 手順4 の規律——1問ずつ聞き、答えをそのまま書き留める。転記であって生成ではない)。停止2は**テンプレートの提示順を守る**(first-review の出力を開くのは記録が済んでから)。**聞き取りの区切りごとに `date +%s` を挟み、実測表にゲート単位で1行ずつ書く**。人間がその場で答えられない・離席する場合は従来どおり止まって終わる(下の報告形式)
   - **停止に属さない `👤`**(第二解釈者の期待値・食い違いの裁定・マージの決断): **止まる**。次の形式で報告して終わる
   - 止まるときの報告形式——**現在地**(固定書式。必ず先頭に):
     ```
     現在地: <停止の列。済んだ停止に ✅、いま止まっている位置に ◀ と👤の名前(仕様書の実行は作業名)>
     進み:   完了 <n> / 全 <m> 項目(👤 は <i> / <j> 通過、停止は <s> / 3)。[-][~] は分母から除く
     未マージ: <`git branch --no-merged <切り元>` の出力をそのまま。切り元が未記録なら行を省く>
     この後: 機械が止まらずに走る工程 <k> 件(内訳)。見込み 約 <下限>〜<上限> 分(根拠: 本チケット実測 / 初期値)
     残りの停止: <残数と、各停止に残る 👤 の名前>
     ```
   - **何が必要か**(1行)/**誰が**(役割名)/**なぜ機械で埋められないのか**(1行)/**判断材料**(ここまでに生成した下書きのパス)/**人間が埋めたら、もう一度このスキルを呼べば続きが走ること**
   - ヘッダの「👤で止めた時刻」に `date` の出力を書く
   - **停止1は、委譲の送信と聞き取りが終わった時点で呼び出しを終える**(実装の完了待ち。テンプレート「継続呼び出し」参照——完了の通知が届く環境ではそのまま自動で続き、届かない環境では人間が呼び直す。どちらも判断ゼロの継続であり、停止には数えない。経過の上限検査はこの呼び出しの先頭で行う)
6. 状態ファイルのヘッダ(チケットの在り処・設計メモの在り処と承認・不可逆系・理解レベル・実データの所在・結合テストの実行手段・実装の委譲先・最終更新・次にやること)を更新して終わる

## 見込み(現在地の1行に使う)

- 参照値は**本チケットの実測**、無ければ下の初期値。下限=合計、上限=その2倍
- 初期値(分。出典: 基準を1周回した記録 TICKET-143——**1回の実測・架空題材**。自分の実測がたまったら使わない): 設計メモ系 1 / 検査の判定と材料の切り出し 1 / **実装の完了確認 4**(結合テストを指示していない時点の実測。v0.39 で委譲の範囲が結合テストまで広がったので、境界を越える変更ではこの値より伸びる——実測が出たら差し替える)/ 自動版 3(生成+実行の合算実測。v0.41 で生成が停止1に移ったので、実行だけの継続呼び出しではこれより短い——内訳は未実測)/ 地図の初版 1 / 突き合わせ・書き戻し 2 / PR下書き・地図同梱 1 / first-review 6 / 欄の検査・記録 1
- **実装の完了確認だけは規模に比例し、上限が無い。** 委譲時にサブエージェントへ「変更するファイル数と見込み(分)」を最初に報告させ、ヘッダの委譲先の行に書く
- **待ちの監視はしない**(待っている最中の flow は時計を見られない)。次に呼ばれたとき、ヘッダの時刻から経過を計算し、委譲の見込み上限(無ければ30分)を超えていたら現在地に「上限超過(<分>)」を1行出し、実測表にも残す(初期値を直す根拠になる)

## セッションの分離(汚染の構成的防止)

人間と対話できるのは、このスキルを実行しているメインセッションだけである。したがって:

- **聞き取り(crosscheck 手順U・A-2)はメインセッションが行う。** 別セッションには置けない
- **同時進行の判定機構は持たない。** v0.30〜34 の作業ツリー検査と親ファイル `_active.md` は削除した——git の観測値から「マージ済みか・実装中か」を判定する機構は、git 運用の前提(未追跡ゼロ・既定ブランチ・マージ方式)を必ずどれか決め打ちし、実測で誤り続けた。squash / rebase マージでは v0.34 の消去条件が永久に偽になる(CHANGELOG v0.35)。「未マージのチケットがある間、同じ作業ツリーへ次の委譲をしない」は README の運用規約であり、flow は守らせない。代わりに**止まって報告するたび、現在地に「未マージ:」の1行を写す**(上の固定書式)。判定しない・消さない・これを理由に止まらない。マージ済みに見えるブランチが残る運用(squash 等)で行を掃除するのは人間の `git branch -D` である
- **人間が実装の並列を明示的に選んだ場合のみ**、`git worktree add <パス> -b <ブランチ> <切り元>` で専用の作業ツリーを作ってから委譲する(切り元が申告ではなく実行になる)。未追跡ファイル(.env 等)と依存物(venv・node_modules)は worktree に来ないことを委譲プロンプトに明記する。マージ後の `git worktree remove` は人間が行う
- **実装はサブエージェント(別セッション)に委譲する。委譲の範囲は実装・単体テスト・結合テストまで**(不可逆系の境界は実物に通さない)。委譲プロンプトにはチケットと承認済み設計メモの所在(どちらもヘッダの記載。設計メモの在り処と承認が未記入なら委譲しない——承認前の実装着手は「絶対にやらないこと」)、**結合テストの実行手段**(ヘッダの記載。「なし」なら「作らず、未実施と報告する」と書く)を含め、**照合メモの内容もパスも含めない**。**作業ブランチ(名前と切り元)と完了報告の置き場所(状態ディレクトリ配下の別ファイル)を指定し、ヘッダの「実装の委譲先」に書く**——次の呼び出しはここから「実装の完了確認」を行う。完了報告には「実装中に迷った箇所・仕様が薄く補完した箇所」と**「結合テストで固定した境界・固定しなかった境界と理由・落ちたまま残したテスト・実物の挙動が地図 Level 1 と違った箇所」**を残させる(実装の完了確認は継続呼び出しの機械工程。**「迷った箇所」を著者が読むのは停止2の先頭、「固定した境界」は種別確定の後**——テンプレートの提示順。将来も参照したい事実は地図かコードコメントへ)
- **委譲は期待値の書き出し(聞き取り)より先に行い、完了を待たずに次の項目へ進む。** 委譲プロンプトを書いた時点で期待値がまだ存在しなければ、「渡さない」が指示ではなく構成で保証され、実装と聞き取りが並列に進む。停止1では**委譲を送信した直後、同じ停止の中で聞き取りを続ける**——順序は同じで、呼び出しが1回にまとまっただけである。順序が逆になった場合は、状態ファイルに**「独立性は指示ベース」**と記録する
- **照合メモと結合テスト仕様書はリポジトリの外、かつ委譲プロンプトに現れるどのパスの祖先でもないディレクトリに置く**(例: `~/.flow-crosscheck/<リポジトリ名>/`)。完了報告の置き場所は状態ディレクトリ配下で委譲プロンプトに書かれるため、**照合メモを状態ディレクトリに同居させると、委譲後に書かれたメモへ実装サブエージェントの探索が届きうる**。リポ内は同じ理由でさらに不可
- **first-review も実装とは別セッション(サブエージェント)で実行する**

## 絶対にやらないこと

- **`👤` の項目にチェックを入れない。埋めない。「不要」と判断して `[~]` にもしない。** スキップの判断も人間のものである。ここが空欄であることがこのフローの設計である(※判定で対象外になった `👤`——独立照合をやらないチケットの「独立照合の期待値」等——を `[-]` にするのは判定の帰結であり、これに当たらない)
- **不可逆系のゲートで「期限まで無返事なら進む」をしない**(明示的な承認まで止まる)。**設計メモの合意より前に実装を走らせない**
- **「既に済んでいる」項目を `[~]` にしない。** `[x]` にして根拠(ファイルパス等)を書く(スキップ表を汚さない)
- **領域を勝手に確定しない**(`👤`)。機械が行うのは **diff からの仮決め**まで——根拠と「機械が決めた」を状態ファイルに明記し、停止2でドメインオーナーの確定に回す。設計メモの「触る範囲」と diff が食い違ったら、その差分を停止2の提示に必ず載せる(意図ではなく diff が事実——マージ要件が見るのは「触る領域」)。切り方は [update-map](../update-map/SKILL.md)
- **地図の初版を「このチケットのスコープを超える」を理由に別チケットへ先送りしない**
- **結合テストの実行手段を委譲の中で新設させない**(ヘッダが「なし」なら委譲プロンプトにその旨を書き、「未実施(実行手段なし)」と報告させる。整備チケットの在り処か「未起票」をヘッダに持ち、止まって報告するたび現在地に写す。**未起票のまま「未実施」を記録した回は実測表の備考に「結合テスト未実施(実行手段なし・未起票)」を1行残す**——「続く」を数える唯一の場所)。**境界を越える変更で結合テストが無いのに「対象外」と書かない**——「未実施」と理由を書く
- **出力との突き合わせで、実データの所在が分からないまま進めない。** 所在は停止1で聞いてヘッダに書くが、**その申告を決め打ちにしない**——突き合わせの前に diff の実際の参照先と照合し、不一致なら `👤` ではない止まり方(現在地+選べる手)で聞き直す(着手時の申告は実装後に陳腐化しうる。黙って古い所在で集計すると、検査自身が、この工程が検出すべき欠陥を生産する)。**代表データを自作しない**——それはこの工程が検出しようとした欠陥の再生産である
- **マージ・プッシュ・デプロイをしない。** マージの決断は `👤` であり、その先の操作も人間が行う

## スキップの扱い

不要な工程は `[ ]` → `[~]` にし、**理由を「スキップした項目と理由」表に書く**(重すぎた / 不要だった / やる気がなかった、のどれかに寄せる。削除手続きの材料)。削除はしない。`[-]`(対象外)はスキップではないので表に書かない——根拠は項目の行に残っている。

## 呼ばれ方

`/flow TICKET-201 <チケットの本文かURL/パス>` のように呼ぶ(2回目以降はIDだけでよい——本文はヘッダの在り処から辿る)。人間の判断で止まる**停止は標準ケースで3回**(着手/PR確認/マージ。テンプレート冒頭)。呼び出しはそれに**実装完了後の継続呼び出し**(判断ゼロ。完了通知が届く環境では自動)を足した回数になる。マージの `👤` で止まった時点で機械の記録は終わっており、マージ後に呼び直す必要はない。

## 守ること

- **状態ファイルは作業中の道具であり、成果物ではない。** チケットが閉じたら人間が消すか、実測表だけを残す。200行を超えたら記録が肥大している
- 実測の追記を省略しない。**このフローを回した記録だけが、基準を削る根拠になる**
- **他チケットと同時に進めているなら、実測表の備考に「同時進行: <ID群> / 実装順: n番目(決めた者)」を残す**(並行と直列の実測を分けて集計するため)。見込みの参照値を取るときは、同時進行の有無が同じ行を優先する
- **著者がエージェントの実装を手で書き換えた箇所があれば、実測表に1行残す**:「手書き: 疑った項目(①指示/②文脈/③設計/④タスクの切り方/⑤役割分割)と、直した手順書(無ければ「未修正」)」。手書き自体は禁止しない。**記録の無い手書きだけが、手順書の欠陥を次の人に隠す**
- 状態ファイルに設計判断や仕様を書かない。仕様はチケット、契約は地図、判断は設計メモとPRに置く。ここは進行状況だけを持つ
