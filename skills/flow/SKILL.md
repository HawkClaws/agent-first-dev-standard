# フローの進行(基準の実行係)

**このスキルは規範を持たない。** 既存の5本(design-memo / crosscheck / pr-guide / first-review / update-map)を、基準が定めた順序で呼び、状態を1つのファイルに記録するだけである。判断は一切しない。

## 状態ファイル

`docs/flow/<TICKET-ID>.md`。無ければ [assets/flow-template.md](assets/flow-template.md) からコピーして作る。
**テンプレートには基準へのリンクを張らない**(コピー先が `docs/flow/` なので相対パスが切れる)。`§4` のような平文で参照する。

このファイルの `👤` 付き項目の一覧が、**このチケットにおけるHuman-in-the-Loopの定義そのもの**である(基準[§7](../../standard.md#s7)・skills/README)。

## 手順

1. **チケットの本文を手に入れる。** IDだけでは足りない——**この基準はチケットの置き場所を規定していない**(Issue・Jira・Notion・リポジトリ内のファイル、どれでもよい)。
   - 引数に本文かその在り処(URL・パス・Issue番号)が渡されていればそれを使う
   - **渡されていなければユーザーに聞く。推測で進めない。** 薄いチケットを勝手に補完すると、それが独立照合の材料(基準[§4](../../standard.md#s4))になり、著者の解釈が仕様に化ける
   - 本文が薄い場合も補完しない。薄いこと自体を設計メモの「未解決の論点」に出す
2. **状態ファイルを読む**(無ければ作る)。引数にチケットIDが無ければ、`docs/flow/` の中で未完了のものを提示して選ばせる
3. 上から見て、**最初の未チェック項目**へ進む
4. その項目が `👤` **でない**なら実行する:
   - 対応するスキルの手順に従う(スキルを持たない工程は基準本文の該当節に従う)
   - 終わったら `[x]` にし、**実測表に所要を1行追記**する
   - 次の項目へ。`👤` に当たるまでこれを繰り返す
5. その項目が `👤` なら**止まる**。次の形式で報告して終わる:
   - **現在地**(固定書式。必ず先頭に。「見積もりと上限」の節に従って埋める):
     ```
     現在地: 1.着手 ✅ → 2.実装 ◀ ここ(👤 理解検査:期待値の書き出し) → 3.PR作成 → 4.レビュー → 5.マージ → 6.記録
     進み:   完了 5 / 全 29 項目(👤 は 1 / 11 通過)。[~] にした項目は分母から除く
     この後: 機械が止まらずに走る工程 3 件(独立照合の材料 → 実装の完了確認 → 自動版)。見込み 約 5〜10 分(根拠: 初期値)
     残りの 👤: 6 個(領域〔一人運用なら機械が決める〕・地図検収〔初版時のみ〕・選別・裁定・理解レベル・マージ)
     ```
   - **何が必要か**(1行)
   - **誰が**(役割名。基準[§8](../../standard.md#s8)の割り当てに従う)
   - **なぜ機械で埋められないのか**(1行)
   - **判断材料**(ここまでに生成した下書きのパス)
   - **人間が埋めたら、もう一度このスキルを呼べば続きが走ること**
6. 状態ファイルのヘッダ(不可逆系・理解レベル・最終更新・次にやること・**見込みと上限**)を更新して終わる

## 見積もりと上限(止まるたびに現在地を、走る前に見込みを)

止まる回数はゲートの数で決まり、このスキルは減らせない。減らせるのは「今どこで、あと何回止まり、次に止まるまで何分走るか」が見えないことである。

**見込みの出し方**(次の `👤` までに機械が実行する工程の所要の合計):

1. 参照値は優先順で取る。①この状態ファイルの実測表 ②`docs/flow/` にある他チケットの実測表の中央値 ③どちらも無ければ下の初期値。**使った根拠を1語で併記する**(「本チケット実測」「docs/flow 中央値(n=3)」「初期値」)
2. **幅で出す。** 下限=参照値の合計、上限=その2倍。参照が初期値のときは1回分の実測しか根拠が無いので、幅を狭めない
3. **「実装の完了確認」だけは規模に比例し、上限が無い。** 委譲時にサブエージェントへ「変更するファイル数と見込み(分)」を最初に報告させ、それを状態ファイルの見込み欄に書く。実測で置き換える
4. 見込みが**10分を超える機械区間に入る前**には、止まらずに1行「ここから約○分、止まらずに走る(内訳: …)」と出してから進む

初期値(単位: 分。出典は基準を1周回した記録 TICKET-143、**1回の実測・架空題材**。自分の実測が3件たまったら使わない):

| 工程 | 初期値 | 備考 |
|---|---|---|
| 設計メモの下書き・契約欄 | 1 | |
| 検査の段と版の判定・材料の切り出し | 1 | |
| 実装の完了確認(=実装の待ち) | 4 | **規模に比例。唯一の上限なし項目** |
| 自動版の実行 | 3 | 実測なし。テスト生成+実行の目安 |
| 地図の初版生成 | 1 | |
| 理解検査の突き合わせ・書き戻し | 2 | |
| 出力との突き合わせ | 2 | 実データの用意は含まない |
| PR下書き・地図の更新同梱 | 1 | |
| first-review | 6 | |
| 欄の突き合わせ検査・実測の追記 | 1 | |

**上限(ずっと動き続けない)**:

- 待ちを伴う工程(実装の完了確認・first-review・自動版)には上限を置く。**上限=見込みの上限値、見込みが無ければ30分**。状態ファイルのヘッダに書く
- 上限を超えたら **`👤` ではない止まり方**で報告する: 経過(分)・サブエージェントの最後の報告・選べる手(そのまま待つ/切って小さく再委譲/人が見る)。項目は `[ ]` のまま、備考に「上限超過で停止」。**判断はしない**——続けるかどうかも人間が決める
- 上限超過は実測表に1行残す(§12 の材料。見積もりの初期値を直す根拠にもなる)

## セッションの分離(汚染の構成的防止)

人間と対話できるのは、このスキルを実行しているメインセッションだけである。したがって:

- **聞き取り(crosscheck 手順U・A-2)はメインセッションが行う。** 別セッションには置けない
- **委譲する直前に作業ツリーを見る。** まず現在ブランチと**切り元ブランチ**を状態ファイルのヘッダに記録する(切り元は人間に聞く。既に書いてあればそれを使う。**既定ブランチを決め打ちしない**——develop や親ブランチから切る運用がある)。次に `git status --porcelain` と、切り元に無いコミットの有無(`git log <切り元>..HEAD`)。未コミットの差分があるか、切り元に無いコミットがあれば、それは**他チケットの未マージ変更**(または人間の作業中の編集)であり、その上に委譲すると2本の変更が同じ作業ツリーで混ざる。委譲せず **`👤` ではない止まり方**(「見積もりと上限」の上限超過と同じ形)で報告する: 差分のファイル数・ブランチ名・選べる手(マージを待つ / 作業ツリーを分けて進める / 構わず委譲する)。**判断はしない。** 人間が「構わず」と答えたら委譲し、実測表の備考に「同時進行: <ID> / 実装順: n番目(決めた者: 人間)」を残す。別 worktree・別リポジトリなら作業ツリーが違うので発火しない(発火しなくてよい)
- **実装はサブエージェント(別セッション)に委譲する。** 委譲プロンプトにはチケットと承認済み設計メモの所在だけを含め、**照合メモの内容もパスも含めない**。**完了報告に「実装中に迷った箇所・仕様が薄く補完した箇所」を残させる**(PR欄「一番怪しい箇所」の転記元。基準[§9](../../standard.md#s9)・[pr-guide](../pr-guide/SKILL.md))
- **委譲は期待値の書き出し(聞き取り)より先に行い、完了を待たずに次の項目へ進む。** 委譲プロンプトを書いた時点で期待値がまだ存在しなければ、「渡さない」が指示ではなく構成で保証され、実装と聞き取りが並列に進む(基準§4「実装と並列」の実現機構)。順序が逆になった場合は、状態ファイルに**「独立性は指示ベース」**と記録する
- **照合メモはリポジトリの外に置く。** 実装サブエージェントはリポジトリを探索するので、リポ内に置くと「渡さない」が構成で保証されない
- **first-review も実装とは別セッション(サブエージェント)で実行する**(基準§7)

## 絶対にやらないこと

- **`👤` の項目にチェックを入れない。** 埋めることもしない。ここが空欄であることがこのフローの設計である
- **不可逆系のゲートで「期限まで無返事なら進む」をしない。** 明示的な承認が出るまで止まる(基準[§7](../../standard.md#s7))
- **設計メモの合意より前に実装を走らせない。** 順序は状態ファイルの並びのとおり
- **`👤` の項目を「不要」と判断して `[~]` にしない。** スキップの判断も人間のものである
- **「既に済んでいる」項目を `[~]` にしない。** `[x]` にして根拠(ファイルパス等)を書く(スキップ表を汚さない。基準[§12](../../standard.md#s12))
- **領域を勝手に決めない**(`👤`)。例外は、どう切っても検収先・境界の持ち主が変わらない場合(一人運用など)——機械が決め、根拠と「機械が決めた」を状態ファイルに明記し、人の検査に回す(基準[§7](../../standard.md#s7))。切り方は基準[§11](../../standard.md#s11)
- **地図の初版を「このチケットのスコープを超える」を理由に別チケットへ先送りしない。** 初版は、その領域に初めて触るPRの中で作る(基準[§12](../../standard.md#s12) 手順2)
- **マージ・プッシュ・デプロイをしない。** マージの決断は `👤` であり、その先の操作も人間が行う

## スキップの扱い

不要な工程は `[ ]` → `[~]` にし、**理由を「スキップした項目と理由」表に書く**。削除はしない。

理由は「重すぎた / 不要だった / やる気がなかった」のどれかに寄せて書く(基準[§12](../../standard.md#s12) 削除手続きの材料)。

## 呼ばれ方

`/flow TICKET-201 <チケットの本文かURL/パス>` のように呼ぶ(2回目以降は状態ファイルがあるのでIDだけでよい)。1チケットにつき、**人間のゲートの数だけ**呼べばよい。

## 守ること

- **状態ファイルは作業中の道具であり、成果物ではない。** チケットが閉じたら消すか、実測表だけを残す。200行を超えたら記録が肥大している
- 実測の追記を省略しない。**このフローを回した記録だけが、基準を削る根拠になる**(基準[§12](../../standard.md#s12))
- **他チケットと同時に進めているなら、実測表の備考に「同時進行: <ID群> / 実装順: n番目(決めた者)」を残す**(テンプレートの注記)。見込みの参照値(「見積もりと上限」①②)を取るときは、同時進行の有無が同じ行を優先する——並行時の人間の待ちは直列時と同じ分布とは限らない
- **著者がエージェントの実装を手で書き換えた箇所があれば、実測表に1行残す**:「手書き: 疑った項目(基準§8 の①指示/②文脈/③設計/④タスクの切り方/⑤役割分割)と、直した手順書(無ければ「未修正」)」。手書き自体は禁止しない。**記録の無い手書きだけが、手順書の欠陥を次の人に隠す**(基準[§8](../../standard.md#s8))
- 状態ファイルに設計判断や仕様を書かない。仕様はチケット、契約は地図、判断は設計メモとPRに置く。
