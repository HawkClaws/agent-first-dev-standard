# 設計メモの下書き(基準[§7](../../standard.md#s7)「先払い」の実装)

実装開始前に、チームに流す数行の方針メモを下書きする。文脈をレビューの席で初めて獲得するのが最も高くつく形であり、それを先払いに変えるためのもの。

## 手順

1. 対象チケットの内容を把握する(引数で渡されなければユーザーに聞く)
2. 関連するコード領域を軽く調査する(触ることになるファイル・モジュール・境界)。目安は**読むファイル5個まで**——方針が書ける程度でよく、深追いしない。ただし**「触る範囲」に挙げるパス・モジュール名は実在を確認したものだけにする**(調査せずに出力したパスは幻視でありうる。整った形式の嘘は白紙より検証されにくい)
3. 以下の形式で**10行を目安**にメモを出力する:

```markdown
## 設計メモ: <チケット名>
- 方針: <どう解くか、1〜2行>
- 触る範囲: <ファイル/モジュールと、他と接する境界>
- 契約(※契約・不変条件・危険領域を変えるチケットのみ): <この変更で成立させる契約を、呼び出しの約束の形で。「この入力を渡せばこの出力が返る。失敗するときはこう失敗する」の3行(基準§2)。**これが独立照合(§4)の材料になる**>
- 採らない選択肢: <検討して捨てた案 → 捨てた理由(判断の軸を1つ添える。例: 何年持たせる前提か)>
- 不可逆な副作用: <スキーマ変更/データ移行/課金/外部送信/削除 の有無。ありなら戻し方>
- 理解レベルの提案: <どの範囲が 行/構造/契約 か(基準[§2](../../standard.md#s2))。**行レベル該当とドメイン中核かはドメインオーナーの確認事項で、この提案では確定しない**([§8](../../standard.md#s8))>
- 懸念点: (著者が記入。**採った方針に残る不安**——「A案で進めるが、ここは不安」。無ければ行ごと削る。機械は生成しない)
- 未解決の論点: <今チームに決めてほしいこと・分からないので助けてほしいこと。無ければ「なし」>
- 未決定事項: <**あえて今決めないこと**——なぜ今決めないか・いつ誰が決めるか。基準で後段に決め手が置かれているもの(理解レベルの確定=レビュー時にドメインオーナー、触る領域=PR作成時)はここに書く。無ければ行ごと削る>
- 応答期限: <この時刻までに異論なければこの方針で着手(不可逆系ありの場合は明示的な承認待ち)>
```

## 守ること

- これは下書きである。**著者が直してからチームに流す**。直せないなら、それは理解不足のシグナル(基準[§3](../../standard.md#s3))
- 「未解決の論点」を無理に生成しない。本当に無いなら「なし」でよい。もっともらしい論点の水増しは合意の質を下げる。「採らない選択肢」も同様——実際に検討していない案をそれらしく並べない
- **「懸念点」は著者だけが書く。** 採った方針に残る不安は著者の判断の残留物であり、機械が書けば捏造になる。この欄は**PRの「一番怪しい箇所」の転記元**になる(基準[§9](../../standard.md#s9)——実装前に書かれた著者の不安と、実装側の申告の2つを機械が転記する)。3区分の整理は [pospome「優秀なエンジニアが書くDesign Docは何が違うのか?」](https://www.pospome.work/entry/2026/08/24/223309) に倣った——代替案(選ばなかった案。不安の無い内容)・懸念点(選んだ案に残る不安・助けてほしいこと)・未決定事項(あえて決めない。いつ誰が)
- **「未決定事項」は「考えていない」と区別するために書く。** 「いつ誰が決めるか」が書けないものは未決定事項ではなく未解決の論点である。書けたものは flow の後段のゲートに対応する(タスク漏れを構造で防ぐ)
- この下書きの「採らない選択肢」はチーム合意用であり、**PRの「採らなかった選択肢」欄への転記元にしない**(基準[§9](../../standard.md#s9)。あちらの転記元は著者本人の発言のみで、AI下書き部分は不可。選別は著者)
- **契約・不変条件・危険領域を変えるチケットでは「契約」欄を必ず埋める。** これが独立照合(基準[§4](../../standard.md#s4))の言う「実装前に書かれた契約の記述」の実体になる——チケットが薄いと、照合の材料がどこにも存在しないまま不可逆系の必須義務が発効してしまう
- **この契約欄は「意図」であって、確定した契約ではない。地図([§11](../../standard.md#s11))に先に書かない。** 地図は現実の記述で、更新されるのは実装後・当該PRの中である([update-map](../update-map/SKILL.md) モード2)。実装前の意図を地図に置くと、月イチの矛盾検査がコードとの乖離として誤検出する。
  **設計メモの契約(意図)とPRで更新された地図の契約(現実)の差は、裁定の対象になる**——実装が逸れたのか、契約の書き方が曖昧だったのか
- ただし、この設計メモの**方針・触る範囲は独立照合に渡してはいけない**(実装の設計図なので汚染源)。渡すのは要求と契約の記述だけである([crosscheck](../crosscheck/SKILL.md) 共通節)
- 方針への異論を受けて合意するのはチームの仕事。このスキルは準備だけを行う
