# 設計の聞き取り

実装開始前に、著者がエージェントの問いに答えて設計を決める。出力は2つ——**設計メモ**(著者の決定の記録。チームは読まなくてよい)と**チーム確認事項**(チームに確認したほうが良い点だけ)。

## 手順

1. 対象チケットの内容を把握する(引数で渡されなければユーザーに聞く)
2. 関連するコード領域を軽く調査する(触ることになるファイル・モジュール・境界)。目安は**読むファイル5個まで**——問いが作れる程度でよく、深追いしない。ただし**「触る範囲」に挙げるパス・モジュール名は実在を確認したものだけにする**(調査せずに出力したパスは幻視でありうる)
3. **聞き取る。** 調査した範囲とチケットから問いを作り、**1問ずつ聞いて、答えをそのまま書き留める。転記であって生成ではない。**
   - **曖昧さが尽きるまで続ける。** 前の答えで新しい問いが開いたら続ける。止めるのは、残る問いが無くなったときか、著者が「ここまで」と言ったとき(そのときは残りを「未解決の論点」に落とす)。方式は [grill-me](https://github.com/mattpocock/skills) に倣った
   - **推奨回答を添える。著者はその上で決める。** 問いごとに、まず**知識か判断か**を分ける
     - **知識**(調べれば決まる: 触る範囲、既存の挙動、切り替えの単位、既存の契約)——推奨ではなく**機械が決めて根拠を示し、著者は見て違和感があれば止める**(選択肢が実質1つの決定は検査として運用する、という基準の規範)。問いの形は「こう読めたが、違うか」
     - **判断**(トレードオフ・前提・不安の扱い・今決めるか)——**推奨を1つだけ**、根拠(調査したどこから・仕様のどこから)と、採らない場合の代替を1つまで添えて出す。**複数案を並べない**(選択式に戻り、機械が作った選択肢に○を付ける形になる)。根拠が無い問いには推奨を付けず、開いた問いのまま聞く
     - 答えは**採用**(推奨のまま)/**修正**/**却下**/**答えられなかった**のどれかとして記録する。区分は機械が付け、著者の言葉は逐語で残す。「それでいい」は採用、それ以外の言葉が出たら修正か却下
     - **採用がその問いで続くなら、その問いは判断ではなかった**(偽の空欄)。知識側に移すか問いから外す。修正・却下が多い問いは推奨が当たらない本物の判断で、残す。**推奨を出すことで、どの問いが本当に判断だったかが実測できる**——出さないと全問が「著者が答えた」に見える
     - **推奨をそのまま採用した答えは、著者本人の発言ではない。** PR「採らなかった選択肢」への逐語転記の出所になるのは、修正・却下した答えと、推奨なしで答えたものだけ(下記「守ること」)
     - **決めたことが構造の制約になったら**(依存方向・型をどの層が持つか・境界を越えてよい呼び出し)、推奨に**構成で守る手段**(Lint ルール・アーキテクチャテスト・型・ツール制限)を1つ添える。採用なら「決めたこと」の「守り方」に1行書き、実装の委譲範囲に入る(新しい境界なので既存コードに違反は無く、同じPRで入れられる)。手段が書けなければ添えない——手順書に書くしかない制約はそう書く
   - 問いの形は対象で変える。**契約**(入力・出力・失敗の仕方)なら「成功したら何が返るか/失敗したらどう失敗するか(そのとき何が残るか)/前提は何か」。**成否の軸が無い点**(参照先の切り替え等)なら「どの出どころを見るか/見つからないときどこへ倒れるか/切り替えの単位は何か/切り替えても変わらないものは何か」。**不変条件**は「その状況が起きたらどうなるか」に変換し、Yes/Noで閉じない
   - 順序の目安: 方針 → 触る範囲と境界 → 契約 → 不可逆な副作用 → 採らない選択肢とその理由 → 懸念 → 今決めないこと(いつ誰が) → 分からないこと
   - **答えられない問いは空欄のまま「答えられなかった」と記録する。** それ自体が結果である(理解不足か仕様の穴)。機械が補完した時点で著者の欄ではなくなる。「特に無い」も答えで、その欄は行ごと削る
   - 最後の問いは固定: **「チームに確認する点は下の推奨でよいか」**(手順4の推奨を見せる。足す・削るは著者。削ったものは削った旨を残す)
4. **チーム確認事項を推奨する。** 聞き取りの答えから、次に当たるものを抜き出して列挙する。推奨するのは**何を聞くか**であって、答えではない。
   - (a) **不可逆な副作用**(スキーマ変更・データ移行・課金・外部送信・削除)——**必ず**。ドメインオーナーの明示承認を求める
   - (b) **契約・境界を変える**——呼ばれる側の領域の持ち主に
   - (c) **他人の領域に触る**——その領域のドメインオーナーに
   - (d) 著者が**「分からない・決められない」と答えた点**
   - (e) 未決定事項のうち、**決め手が他人にあるもの**
   - 当たるものが無ければ「チーム確認事項: なし」。**不可逆系が無く確認事項も無ければ、チームに聞かずに着手してよい**
5. 次の形式で出力する。**先頭は決めたこと、次にチーム確認事項、聞き取りの記録は末尾に畳む。** 長さは決定の数に従う(行数の上限は置かない。1決定1行の上限だけ守る)

```markdown
## 設計メモ: <チケット名>

### 決めたこと(1件1行)
- 方針: <どう解くか>
- 触る範囲: <ファイル/モジュールと、他と接する境界。実在確認済みのもののみ>
- 契約(※契約・不変条件・危険領域を変えるチケットのみ): <「この入力を渡せばこの出力が返る。失敗するときはこう失敗する」の3行。**独立照合の材料になるので、ここだけは方針と分けて書く**>
- 採らない選択肢: <案 → 捨てた理由(判断の軸を1つ)>
- 不可逆な副作用: <有無。ありなら戻し方>
- 守り方(※構造の制約を決めたチケットのみ): <制約 → 構成で守る手段(Lint ルール・アーキテクチャテスト・型)。実装の委譲範囲に入る>
- 理解レベルの提案: <どの範囲が 行/構造/契約 か。行レベル該当とドメイン中核かはドメインオーナーの確認事項で、ここでは確定しない>
- 懸念点: <採った方針に残る不安。無ければ行ごと削る>
- 未決定事項: <あえて今決めないこと——なぜ今決めないか・いつ誰が決めるか。無ければ行ごと削る>
- 未解決の論点: <分からないので助けてほしいこと。無ければ「なし」>

### チーム確認事項(<n>件。応答期限: <この時刻までに異論なければ着手。不可逆系ありなら明示承認待ち>)
- [ ] <確認したい点。宛先(役割)と、なぜ確認が要るか(上の (a)〜(e) のどれか)を添える>

<details><summary>聞き取りの記録(<問の数> 問・採用 <n>・修正 <n>・却下 <n>・答えられなかった <n>)</summary>

- Q: <問い> / 推奨: <推奨と根拠。知識なら「機械が決めた: 根拠」> / A: <答えをそのまま> [採用/修正/却下]
- Q: <問い> / 推奨: (根拠なし。開いた問い) / A: (答えられなかった)
</details>
```

## 出力の置き場所と回答の記録

このスキルの出力はテキストであり、ファイルには書かない。**置くのは著者で、置き場所はチケットと同じ場所**(チケットの本文への追記か、チケットへのコメント。基準はチケットの置き場所を規定しないので、Issue・Jira・Notion・リポ内ファイルのどれでもよい)。

- **なぜチケットと同じ場所か。** 設計メモは「実装前に書かれた意図」で、独立照合が解釈のもとにする材料の一つ(契約欄)であり、実装の委譲プロンプトの入力でもある。同じ性質の材料(チケット本文)と同じ場所にあれば、後段のスキルは1つの在り処から両方を辿れる。実装後の現実を記述する地図(PRに同梱)とは寿命も読み手も違うので、リポジトリの `docs/` に意図の文書として独立に置かない——PR同梱の意図文書は更新が止まることが実証されている(ADR調査)。チケットが閉じれば設計メモも役目を終える
- **チームに読ませるのは確認事項だけ。** 設計メモ本体は著者の記録で、共有は合意の条件ではない。読みたい人が読める場所にあればよい
- **回答の記録。** 確認事項への回答が揃ったら(期限までに異論なし、または不可逆系での明示承認)、メモの末尾に `確認: YYYY-MM-DD <回答者の役割> (<n>件)` を1行追記する(確認事項が0件なら `確認: 不要(0件・不可逆系なし)`)。これが「承認済み設計メモ」の実体である。この後にメモを書き換えるのは裁定の書き戻し([crosscheck](../crosscheck/SKILL.md) 手順C)だけで、**上書きではなく追記**にする(裁定前の記述が消えると「仕様が2通りに読めた証拠」が消える)
- **在り処と確認の記録は flow の状態ファイルのヘッダに書く**([flow](../flow/SKILL.md))。委譲プロンプト・crosscheck の材料の切り出しはここから辿る。人間に聞くのは在り処(URL・パス)と回答日・回答者だけで、判断ではなく知識の申告——👤 には数えない

## 守ること

- **聞き取りの答えのうち、修正・却下した答えと、推奨なしで答えたものが著者本人の発言である。** PRの「採らなかった選択肢」への逐語転記の出所になる(選別は著者。[pr-guide](../pr-guide/SKILL.md))。**推奨をそのまま採用した答え**と、機械が作った問い・推奨の文言は転記元にならない。「懸念点」も同じ——推奨を採用した懸念は「機械の提案・著者が採用」と記録する
- **「懸念点」「採らない選択肢」「未決定事項」は著者の答えだけで埋める。** 無理に生成しない。本当に無いなら行ごと削る。もっともらしい論点の水増しは合意の質を下げる
- **「未決定事項」は「考えていない」と区別するために書く。** 「いつ誰が決めるか」が書けないものは未決定事項ではなく未解決の論点である。書けたものは flow の後段のゲートに対応する(タスク漏れを構造で防ぐ)
- **契約・不変条件・危険領域を変えるチケットでは「契約」欄を必ず埋める。** これが独立照合の言う「実装前に書かれた契約の記述」の実体になる
- **この契約欄は「意図」であって、確定した契約ではない。地図に先に書かない**(意図と現実の差の裁定は [crosscheck](../crosscheck/SKILL.md) 手順C)
- **独立照合に渡すのは要求と契約の記述だけ**である。方針・触る範囲・聞き取りの記録は実装の設計図なので汚染源([crosscheck](../crosscheck/SKILL.md) 共通節)
- 確認事項への異論を受けて決めるのはチームの仕事。このスキルは準備だけを行う
