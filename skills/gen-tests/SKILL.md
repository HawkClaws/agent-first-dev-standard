# 独立テスト生成(基準§4の実装)

同じセッションが実装とテストを書くと、検証ではなく同語反復になる(エージェントは実装に合わせたテストを書く)。仕様を2回独立に解釈させ、突き合わせることで循環を断つ。

## 手順

1. 対象の**仕様**と**インターフェース**(関数シグネチャ・型・API定義)を特定する。仕様は**実装前に書かれたもの**(チケット・承認済み設計メモの**要求・契約の記述部分**)に限る:
   - 実装後にAIに書かせた仕様サマリは使わない(仕様経由で循環が復活する)
   - 設計メモから渡すのは要求・契約の記述だけ。**方針・触る範囲(実装の設計図)は渡さない**(実装側の解釈を事前共有すると「2回の独立解釈」が崩れる)
2. **ファイル読み取り・検索ツールを持たないサブエージェント**を起動し、仕様テキストとインターフェース定義だけを渡して「この仕様とインターフェースを満たすテストを書け」と指示する:
   - Claude Code なら `.claude/agents/` に Read / Grep / Glob / Bash を外したエージェント定義を置いて使う(例は下記)。プロンプトの「実装を読むな」は防壁ではない——動くテストを書くために設定や既存コードを読みに行く動機がサブエージェント側に常にある
   - ツール制限ができない環境では、リポジトリ外の素のチャット(可能なら**別ベンダーのモデル**。同じモデル同士は同じ読み間違いをしやすい)に仕様とインターフェースを貼って生成させる
   - 同一コンテキスト内で「サブエージェントのつもり」で書いてはいけない。実装が見えている時点でこのスキルの意味が消える
3. 生成されたテストを実装に対して実行する。import パス等の**実行のための機械的修正**はよいが、**落ちたテストのアサーションや期待値を実装に合わせて直してはいけない**——落ちたテストは修正対象ではなく裁定対象(手順5)
4. 結果を分類して報告する:
   - **通ったテスト** → 契約の固定として採用候補
   - **落ちたテスト** → バグである以前に**仕様が2通りに読めた証拠**。仕様のどの記述がどう曖昧だったかを特定して提示する
5. 裁定を求める。**どちらの解釈が意図かを決めるのは仕様の持ち主(人間)**。仕様の持ち主が著者本人の場合、不可逆系の裁定にはドメインオーナーを加える(利益相反)。裁定結果は仕様・設計メモに書き戻す

ツール制限付きエージェント定義の例(`.claude/agents/spec-test-writer.md`):

```markdown
---
name: spec-test-writer
description: 仕様とインターフェースだけからテストを書く。実装コードへのアクセスを持たない。
tools: []
---
渡された仕様とインターフェース定義だけを根拠にテストコードを書く。
実装の中身を推測で補完せず、仕様に書かれていない挙動には
「仕様に記述なし」とコメントを付けてテスト対象から外すか、素直な解釈で書く。
```

## 守ること

- サブエージェントのコンテキストに実装コードを入れない。**入れた時点で循環が復活する**。ただしこの条件は実装コードだけでは足りない——実装後生成の仕様・設計メモの方針欄・CLAUDE.md のアーキテクチャ記述も同じ汚染経路になる(手順1)
- **隔離が破れても出力からは分からない**(テストは緑で返ってくる)。確認できる環境では、サブエージェントのツール使用ログに実装ファイルへのアクセスがないことを確認する。ツール制限なし・ログ確認なしで実施した場合は、PRの裁定記録に「独立性は指示ベース」と明記する(「独立検証済み」のラベルが実態より強く読まれるのを防ぐ)
- 2つのセッションが同じ読み間違いに合意した場合、テストは緑のまま通る。不一致は検出できるが、**一致の正しさは保証されない**。最後に著者へ「自分で追加のエッジケースを1〜2個考える」ことを促して終える
- 適用は構造理解以上。**不可逆系(スキーマ・データ移行・課金・外部送信・削除)には必須、それ以外の構造理解対象には推奨**。契約レベルのコードには過剰装備
