# 独立テスト生成(基準§4の実装)

同じセッションが実装とテストを書くと、検証ではなく同語反復になる(エージェントは実装に合わせたテストを書く)。仕様を2回独立に解釈させ、突き合わせることで循環を断つ。

## 手順

1. 対象の**仕様**(チケット・設計メモ・契約の記述)と**インターフェース**(関数シグネチャ・型・API定義)を特定する
2. **サブエージェントを起動**し、次の2つ**だけ**を渡す:
   - 仕様のテキスト
   - インターフェース定義
   - 指示:「この仕様とインターフェースを満たすテストを書け。実装コードは読むな・探すな」
3. 生成されたテストを実装に対して実行する
4. 結果を分類して報告する:
   - **通ったテスト** → 契約の固定として採用候補
   - **落ちたテスト** → バグである以前に**仕様が2通りに読めた証拠**。仕様のどの記述がどう曖昧だったかを特定して提示する
5. 裁定を求める。**どちらの解釈が意図かを決めるのは仕様の持ち主(人間)**。裁定結果は仕様・設計メモに書き戻す

## 守ること

- 手順2でサブエージェントのコンテキストに実装コードを入れない。**入れた時点で循環が復活する**。これがこのスキルの唯一にして絶対の条件
- 可能なら実装とは別ベンダーのモデルを使う(同じモデル同士は同じ読み間違いをしやすい)
- 2つのセッションが同じ読み間違いに合意した場合、テストは緑のまま通る。不一致は検出できるが、**一致の正しさは保証されない**。最後に著者へ「自分で追加のエッジケースを1〜2個考える」ことを促して終える
- 適用は構造理解以上・不可逆系(スキーマ・データ移行・課金・外部送信・削除)に絞る。契約レベルのコードには過剰装備
