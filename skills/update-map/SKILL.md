# 理解の地図の生成・更新(基準[§11](../../standard.md#s11)の実装)

コード量が増えても、人間が理解すべき情報量が増えない構造にするための地図を維持する。コードとドキュメントの齟齬は必ず発生する——このスキルの目的は「齟齬が起きない」ことではなく、**「齟齬に気づける」**ことである。

## 地図の仕様

- **置き場所: `docs/map/<領域>.md`。領域(ドメインオーナーの担当単位)ごとに1ファイル。** 領域が1つのプロジェクトでは `docs/map/` にファイル1枚でよい(領域名はリポジトリ名かサービス名)。**領域の切り方を決めるのは人間**——この切り方が検収先・マージゲートの発効単位・境界をまたぐ契約の持ち主を決めてしまう。**領域はリポジトリをまたがない**(基準[§11](../../standard.md#s11))——地図ファイルは1つのリポジトリにしか置けず、またぐ切り方をすると他方のリポジトリのPRが「更新は当該PRに同梱」を満たす手段を失う。
  - CLAUDE.md 等のエージェント設定ファイルには本文を埋め込まず、リンクだけを置く。理由は2つ:①全セッションに自動注入されるファイルにアーキテクチャ記述を置くと、独立照合([crosscheck](../crosscheck/SKILL.md))の汚染経路になる——自動版だけでなく、人間版で人間が読む材料も汚染される。②人間が読む場所とAIが常時読む場所を分けることで、分量管理が独立にできる
- **分量: 1領域あたり200行以内。** 超えたら追記ではなく、削る対象を探す。読まれない地図は理解負債の別の形にすぎない(基準[§11](../../standard.md#s11))。
  **プロジェクト全体で200行ではない**——大規模では Level 1 だけで上限を超えるので、領域で割る。逆に、領域の地図が200行に収まらないなら、それは領域の切り方が大きすぎるというシグナルである(ドメインオーナー1人が担当しきれない範囲になっている)
- **領域に属さないコード(共通基盤・共有ライブラリ・認証ミドルウェア等)も1つの領域として扱い、ドメインオーナーを決める。** 担当が決まらないコードは領域ファイルを持たないので、[first-review](../first-review/SKILL.md) の検査項目6が**恒久的に「未検査(地図なし)」を吐き続ける**。領域の切り方に漏れがあることが、そこで沈黙ではなく反復として出る。
- **領域が2つ以上あるなら `docs/map/README.md` に Level 0 を置く。** ただし書くのは**領域の境界と、境界をまたぐ契約だけ**。領域の内部は各領域の地図に置く。ここに全体を書くと上限が意味を失う
- **各ファイルの冒頭にメタデータヘッダーを置く**(基準[§11](../../standard.md#s11)。freshness は Google の g3doc に倣う)。様式は次の4キーで固定:

  ```markdown
  ---
  type: Domain Map
  description: <この領域の1行説明>
  owner: <ドメインオーナー>
  reviewed: <人間が最後に検収した日 YYYY-MM-DD>
  ---
  ```

  - `type` — 固定値 `Domain Map`。更新不要。地図ファイルをパス規約に依存せず機械識別するためのキー。OKF v0.2 の必須キーと同形なので、OKFリーダーにもこのまま読める(準拠は名乗らない。判断は CHANGELOG v0.11)
  - `description` — この領域の1行説明。一覧・検索・AIの読み込みで使う
  - `owner` — 検収と維持の責任者(ドメインオーナー。基準[§8](../../standard.md#s8))
  - `reviewed` — 人間が最後に検収した日。**書き換えてよいのは人間の検収時(初版検収・矛盾検査の齟齬判定後)だけ**。このスキルは下書きに `reviewed: (未検収)` と書き、勝手に日付を入れない。古い `reviewed` の検出はCIの1行でできる(例: 90日超をfail)
- **構成:**
  - Level 0 システム地図 — 何がどこにつながっているか(mermaid 1枚)
  - Level 1 契約 — 主要コンポーネントごとに入出力・副作用・失敗時挙動を1〜3行
  - Level 2 不変条件 — 絶対に壊してはいけないこと(箇条書き)
  - Level 3 危険領域 — 不可逆系(スキーマ・データ移行・課金・外部送信・削除)の位置と、失敗時に何が起きるか・戻し方
- Level 4(実装)は地図に書かない。必要時にAIに絞り込ませて降りる

## モード

### 1. 初版生成(トリガー: **その領域に初めて触るPRの中**。地図が無い領域で更新・矛盾検査を求められたとき)

1. **まず領域を決める**(ドメインオーナーの担当単位。[§8](../../standard.md#s8))。**全領域を一度に作らない**——領域を1つずつ生成・検収でき、**その領域に触るPRのマージゲートが領域ごとに発効する**(基準[§12](../../standard.md#s12) 手順2)。大規模リポジトリで「全体の地図ができるまで全PRがゲート未発効」になるのを避けるため
   - **「同じファイルを触るから同じ領域」では切らない**(実測: この誤読で既存の地図の守備範囲を不当に広げ、撤回になった)。手掛かりは2つ——①その地図の `description` 1行で、今回の変更も含めて説明できるか ②更新条件が混ざらないか(片方だけを変える変更が、もう片方の記述の更新を要求しないか)。迷ったら既存の地図を広げるより分ける(分量の上限は1領域あたり。基準[§11](../../standard.md#s11))
   - **初版を「このチケットのスコープを超える」を理由に別チケットへ先送りしない**——その領域に初めて触るPRの中で作る(基準[§12](../../standard.md#s12) 手順2)。一人運用など、どう切っても検収先・境界の持ち主が変わらない場合は、機械が決めて根拠と「機械が決めた」を記録し、人が見て止める形でよい(基準[§7](../../standard.md#s7))
2. その領域のコードを調査し、上の構成・分量で下書きを生成する。取捨の基準は「保守する人間が**障害・変更・意思決定のとき**に必要な知識か」。網羅ではない
3. 生成後、**その領域のドメインオーナーに検収を求める**。この初回修正が地図の検収であり、所有(基準[§11](../../standard.md#s11))の実体。検収した人間が `reviewed` に日付を入れる(これが検収の記録になる)
   - **検収の最低ラインは Level 2(不変条件)と Level 3(危険領域)の通読・修正である。** 障害時に切り分けの根拠になるのはここで、誤り(「このデータは削除されない」と書かれているが実際は削除経路がある等)が通過すると、障害時に確実に誤った切り分けをする。Level 0・1 の誤りは実害が小さく、月イチの矛盾検査(モード3)でも拾える。200行の全通読を要求して検収そのものが形骸化するより、最低ラインを確実に守らせる
   - **機械による事実検証の併用を認める。** 検収の前処理として、**別セッションのエージェント**に地図の各主張を一次ソース(コード)と突き合わせさせ、「誤り/疑わしい/確認済み」に分類させてよい(モード3と同じ機構。生成したセッション自身にやらせるのは自己検査で無意味)。**検証は検収の代替ではない**——`reviewed` を書き換えてよいのは人間だけ、という規律は変わらない。検証は人間が読む箇所を絞るための前処理である
   - 検証で「疑わしい」と判定され、人間もその場で確定できない記述は、**消さずに「(未確認)」と明記して残す**——消すと同じ調査が繰り返される
   - 無修正で受け入れられた地図は読まれていない疑いがある——直す箇所が1つもない生成物は稀である(実測: さらっと読んで無修正で通した初版に、後の機械検証で誤り6件。うち不変条件2件・危険領域2件——警告はそのまま当たった)

### 2. 更新(トリガー: 契約・不変条件・危険領域を変えるPRの中/障害対応の後)

1. 判明した事実(裁定結果・障害で判明した依存・新しい危険領域)を該当Levelに反映する下書きを作る
   - **契約・不変条件・危険領域を変える変更の場合、地図の更新は当該PRに同梱する**(マージ後に回さない)。マージ時点で「地図で追跡できる状態」を確認できないと、基準[§3](../../standard.md#s3)のマージゲートが空文になる
   - 事後の更新になるのは、**障害対応で判明した事実の書き戻し**だけである
2. 分量上限を守る。追加するなら、**古くなった記述の削除候補を同時に提示する**

### 3. 矛盾検査(定期: 月イチ目安。CIジョブ化も可)

1. 地図の記述とコードの現状を突き合わせ、齟齬を列挙する——地図にあるが存在しないコンポーネント、変わった契約、地図に載っていない不可逆系。境界をまたぐ契約は片側からしか見えないので、**呼ぶ側の領域の検査では「自コードの実際の呼び方 vs 参照先(呼ばれる側)の契約」の突き合わせも行う**——これを省くと契約の当事者の一方が恒久的に検査圏外に落ちる
2. 出力は「齟齬リスト+修正案」。**勝手に直さない**——コードが正しく進化したのか、地図が正しくてコードが逸脱したのかの判定は人間の仕事
3. 人間が齟齬を判定し終えたら(齟齬0件の確認も含む)、その人間が `reviewed` を更新する。検査せずに日付だけ進めるのは「未検査」を「検査したが齟齬なし」に偽装する行為であり、やらない

## 守ること

- 地図の所有者は人間。このスキルは下書きと検査だけを行う
- 矛盾検査で**Level 3(危険領域)に関する齟齬**が出た場合は、他の齟齬と混ぜず先頭に単独で出す([first-review](../first-review/SKILL.md) のBLOCKER枠と同じ理由)
- 「検査したが齟齬なし」と「未検査」を区別して報告する
- 地図がまだ無いリポジトリで更新・矛盾検査を求められたら、初版生成から始めることを提案する
