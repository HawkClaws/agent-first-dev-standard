# AI一次レビュー(基準§7の実装)

人間レビューの代替ではなく**前処理**。機械的に検査できるものを先に潰し、人間を設計判断と契約の妥当性に集中させる。

## 検査項目

1. **規約・スタイル**: プロジェクトの規約(CLAUDE.md・lint設定・既存コードの慣習)との不整合
2. **テストと実装の整合**: テストが契約(入出力・失敗時の挙動)を表しているか。アサーションの無いテスト、実装の挙動をなぞっただけのテストを指摘する
3. **Happy Path偏り**: 異常系・境界値のテスト欠落。特に、仕様に失敗時挙動の記述があるのにテストが無い箇所
4. **レビュー指定の突き合わせ**: PRの「レビュー指定」とdiffの実態を照合する。不可逆な副作用(スキーマ・データ移行・課金・外部送信・削除)を持つ変更が契約レベル扱いになっていたら警告する
5. **隔離の確認**: 契約レベル指定のコードが安定したインターフェースの後ろに隔離されているか(基準§5)。ドメイン中核に編み込まれていたら警告する
6. **地図との整合**: diffが契約・不変条件・危険領域(地図 `docs/map.md` のLevel 1〜3)を変えるかを判定し、変えるのに地図の更新がPRに含まれていなければ指摘する([update-map](../update-map/SKILL.md)で更新できる旨を添える)。地図がまだ存在しないリポジトリでは「未検査(地図なし)」と報告し、**[update-map](../update-map/SKILL.md) の初版生成から始められる旨を添える**——「地図なし」を正常系として黙って通すと、地図が無い状態から抜けるきっかけがフローのどこにも無くなる(基準§12 手順2)

## 出力

出力は3ブロックに分け、この順で出す:

1. **BLOCKER(単独枠)**: 検査項目4の不可逆系誤分類警告。**他の指摘と混ぜない**——スタイル指摘の中に埋めると警報疲れで流される。該当なしなら「不可逆系の誤分類: なし(検査済み)」と1行書く
2. **機械的指摘**(重要度順、各指摘に根拠と該当箇所): lint的に判定できたもの(規約違反、アサーション無しテスト等)
3. **所見**(判断の候補であって判定ではない): 「テストが契約を表しているか」「Happy Path偏り」「隔離されているか」など、本来は人間の判断に属するもの。**所見は精読の候補箇所の提示であり、「問題なし」という所見は合格印ではない**ことを明記する

最後に「人間レビューで見るべき箇所」の要約(設計判断・契約の妥当性・構造理解対象のデータフロー・行レベル対象の精読ポイント)を付ける。

## 守ること

- **実装を書いたセッションとは別セッションで実行する。** 同一セッションで実行すると、自分がなぞって書いたテストを自分で検査する自作自演(基準§4)に戻る
- **このスキルは独立照合(基準§4)ではない。** 検査項目2で「テストが契約を表しているか」を見るが、それは**実装を読んだうえでテストを見ている**——判断のアンカーが実装側にあり、仕様の別の読み方は出てこない。別セッションで実行しても、この性質は変わらない。**独立照合の代わりに使わないこと**(不可逆系では、このスキルの実行は独立照合の実施を意味しない)
- **承認・マージの判断や推奨はしない。** それはマージした人の責任である(基準§8)。「マージしてよさそうです」の類も書かない
- 指摘の採否は人間が決める。AIレビュー指摘の却下率が高いのは正常な運用であり(第三者評価では過半が却下される)、指摘を通すことを目的にしない。ただし**BLOCKER枠の警告は「いつもの指摘」と一緒に一括却下される設計にしない**のがこの出力形式の目的である
- 見つからなかった観点は「検査したが指摘なし」と明示する。沈黙と合格を区別できるようにする。ただし「指摘なし」と書けるのは実際にその観点でdiff全体を検査した場合だけ——検査していない観点は「未検査」と書く
